# histgraph — 한국사 온톨로지 그래프

역사를 인물·사건·장소·작품·유물·영상물의 노드와 엣지로 연결해 보여주는
프로젝트. 이 저장소는 그 **데이터 수집 파이프라인**이다.

## 빠른 시작

```bash
cp .env.example .env        # 인증키 입력
uv sync --extra mlx         # 환경 구성 (추출은 mlx 가 있어야 돈다)

uv run histgraph doctor                          # 소스별 접근 진단
uv run histgraph ingest heritage --kinds 11 12   # 국보·보물 수집
uv run histgraph ingest wikidata                 # 인물/사건/영상물 수집
uv run histgraph prune                           # 스포츠 이벤트 제거 (필수)
uv run histgraph reclassify                      # 개념을 사건에서 갈라냄 (필수)
uv run histgraph works                           # 역사를 다룬 작품 명단 (위키백과 분류)
uv run histgraph enrich --types media --full     # 작품 본문 (works 뒤에)
uv run histgraph namu                            # 토막글 작품은 나무위키 개요·줄거리로
uv run histgraph resolve                         # 소스 간 엔티티 연결
uv run histgraph events                          # 사건·단체·개념 시드 수집 (이름으로 직접)
uv run histgraph enrich                         # 위키백과 서사로 노드 보강
uv run histgraph extract --dry-run               # 추출 프롬프트 확인
uv run histgraph extract --min-score 2.0 --limit 50   # 관계 추출 (배치)
uv run histgraph promote --dry-run               # 추출 고아 승격 계획 확인
uv run histgraph promote --prune-orphans         # ex: 노드를 실제 노드로 병합
uv run histgraph relabel                         # 영어로 들어온 이름을 한국어로
uv run histgraph redescribe                      # 영어로 들어온 설명을 한국어로
uv run histgraph reigns                          # 왕의 재위·대통령의 재임 기간 (P39 한정어)
uv run histgraph corpus                          # 근현대 문서 전문 -> data/corpus.sqlite (RAG 저장층)
uv run histgraph ask "체포 명단"                 # 말뭉치 검색 (모델 없음)
uv run histgraph roles --dry-run                 # 참여 엣지의 역할 판정 (근거 문단 유무만)
uv run histgraph precision                       # 연도만 아는 날짜의 1월 1일을 걷어냄
uv run histgraph links                           # 사건끼리의 상하위·전후 관계
uv run histgraph stats                           # 그래프 통계
uv run histgraph spans --types event org         # 연대 없는 노드에 연대 채우기
uv run histgraph scope korea                     # 조선~대한민국을 화면용 DB 로
uv run histgraph show wd:Q37682 --depth 2        # 세종 주변 서브그래프
uv run histgraph serve                           # 브라우저에서 탐색
```

**`prune` 과 `reclassify` 는 선택이 아니라 필수입니다.** 아래 "스포츠 오염"과
"개념이 사건 행세를 하고 있었다" 참조.

**`relabel`·`redescribe`·`reigns`·`precision` 은 수집 뒤마다 다시 돌려야 합니다.**
`upsert_nodes` 는 라벨을, `upsert_edges` 는 `props` 를 통째로 덮어씁니다.
그래서 다시 수집하면 한국어 이름이 영어로 되돌아가고, **연표 왼쪽의 왕
재위 띠가 통째로 사라집니다** — 재위는 `held_position` 엣지의
`props.reign` 표식으로만 서 있는데 `ingest wikidata` 가 같은 P39 엣지를
다시 넣으면서 그 표식을 지우기 때문입니다 (실측: 재위 26건 → 0건, 화면의
'왕 24/26' 칩과 띠가 함께 사라졌다). 시대 그래프는 별도 파일인데, 거기에는
`scope` 가 `relabel`·`redescribe` 를 **스스로 돌리고** 그러고도 영어가
남으면 실패로 끝난다 (2026-09-04). push 전 훅과 CI 가
`tools/check_korean.py` 로 같은 것을 다시 센다 — [CLAUDE.md](CLAUDE.md) §1.
`precision` 은 날짜 칸을 고치는데 `upsert_nodes` 가 새 값으로 덮어쓰므로
(`COALESCE(excluded…)`), 다시 수집하면 1월 1일이 되돌아옵니다.
아래 "영어로 뜨는 노드"·"영어로 뜨는 설명" 참조.

환경은 uv 가 잡는다 (Python 3.11+). 본체는 표준 라이브러리만 쓰고,
서드파티는 추출 백엔드에만 붙는다 — `--extra mlx` 는 로컬 추출(Apple
Silicon), `--extra anthropic` 은 원격 추출. 둘 다 없어도 수집·화면은 돈다.

## 설계에서 가장 중요한 사실

**공공 API 는 개체를 주지만 관계를 주지 않는다.** 그래프의 가치는 엣지에
있는데, 국가유산청·공공데이터포털은 유물 속성(명칭·소재지·시대)은 잘 주지만
"누가 이 사건에 참여했는가" 같은 관계는 제공하지 않는다.

Wikidata 조차 부족하다. 실측치:

| 관계 (조선) | 엣지 수 |
|---|---|
| 직업 P106 | 3,595 |
| 자녀 P40 | 647 |
| 출생지 P19 | 431 |
| 아버지 P22 | 402 |
| **참여 사건 P1344** | **35** |

계보·출생지는 수집으로 채워지지만, **역사 서사의 핵심인 인물↔사건 엣지는
거의 존재하지 않는다.** 이 엣지는 산문(국가유산청 `content`, 실록 원문,
백과사전 항목)에서 추출해야 한다. `Edge.confidence` 필드가 그 대비다 —
구조화 소스는 1.0, 텍스트 추론은 그 미만으로 기록해 신뢰도를 구분한다.

### 스포츠 오염 — 총계만 보면 속는다

정체 9개로 넓혀 수집하면 `participated_in` 이 5,791건까지 늘어난다.
충분해 보이지만 **90.5%가 올림픽·아시안게임 출전 기록**이었다.

| 단계 | participated_in |
|---|---|
| 수집 직후 | 5,791 |
| 라벨 정규식 제거 후 | 125 |
| Wikidata 클래스(P279*) 제거 후 | **85** |

남은 85건이 진짜다 — 국채보상운동(26), 제1차 왕자의 난(6), 계유정난,
전조선 제정당사회단체 대표자 연석회의. 처음 조선만 측정했을 때의 35건과
같은 크기다. 정체를 넓혀도 역사 엣지는 늘지 않았다.

**교훈: 엣지 총계가 아니라 대상 노드의 라벨 분포를 봐야 한다.**
필터는 라벨 정규식만으로는 부족하다 — 'Konica Cup', 'Superseries',
'Internationaux de France' 는 이름만으로 스포츠인지 알 수 없다.
Wikidata 의 P279* 계층에 직접 물어보는 2차 필터가 필요하다.

### 개념이 사건 행세를 하고 있었다 (`reclassify`)

작품 96편이 역사에 붙어 있는 것처럼 보였다. `depicts` 엣지가 157건이었다.
**그중 실제 역사 사건을 가리키는 것은 6건이었다.**

| depicts 가 가리키던 것 | 엣지 |
|---|---:|
| 조직범죄 | 20 |
| 보복 | 11 |
| 연쇄살인범 | 7 |
| **6.25 전쟁** | **6** |
| 자살 · 시간 여행 · 사형 · 성매매 … | 나머지 전부 |

원인은 `fetch_media` 의 한 줄이었다. Wikidata 의 P921(주제)이 무엇인지
묻지 않고 사건으로 가정했다.

```python
# 소재의 실제 타입은 미확정 — 사건으로 가정하고, 다른 소스가 같은
# QID 를 더 정확한 타입으로 덮어쓰면 갱신된다.
nodes.setdefault(sid, Node(..., type="event", ...))
```

덮어쓸 다른 소스는 오지 않았고, '자살'·'간통죄'·'조직범죄'가 사건 노드로
앉았다. **스포츠 오염과 같은 모양이다 — 총계가 아니라 대상 노드의 라벨
분포를 봐야 보인다.**

P921 은 대개 역사가 아니다. 한국 영화·드라마의 주제 500건 중 447건이
부류(개념)였고 사람은 10건이었다. 이제 `fetch_media` 는 같은 질의에서
인물 여부를 함께 묻고, **판정이 안 서면 개념으로 떨어뜨린다** — 개념을
사건으로 올리기는 쉽고, 사건 틈에 낀 개념은 나중에 찾아내기 어렵다.

#### 지우지 않고 옮긴다

주제어는 쓰레기가 아니라 **자리를 잘못 찾은 개념**이다. `concept` 타입과
`about` 엣지를 만들고 그리로 옮긴다. `reclassify` 가 그 일을 한다.

#### 판정은 점수가 아니라 사다리다

```
1. P31 에 Q5(사람)가 있으면            → 인물
2. 주제 자리에만 있고 사실층에 안 닿으면  → 개념
3. 참여자·발생지가 붙어 있으면          → 사건
4. 동음이의어·목록 문서면               → 보류
5. P279(상위 부류)를 갖고 있으면
     시점(P580/P585)이 있으면          → 사건
     없으면                          → 보류
6. 클래스가 없거나 조회에 실패하면        → 보류
7. 클래스가 사건 계층에 닿으면           → 사건
8. 클래스가 매핑표에 있으면              → 그 타입
9. 그 밖에는                          → 보류
```

이 순서는 하나씩 틀려 가며 만들어졌다. 되풀이하지 말 것:

- **P279 만으로 개념이라고 하면 안 된다.** 신유박해(참여 28건)·제2차 세계
  대전·메이지 6년 정변이 P279 를 갖고 있어 개념으로 넘어갔다. 한국사
  항목에는 부류이면서 개별 사건인 것이 섞여 있다. 가르는 것은 **시점**이다 —
  진짜 부류('자살'·'전쟁'·'살인'·'조직범죄')는 하나도 P580/P585 를 갖고
  있지 않다.
- **사건 계층(P31/P279* → Q1190554)을 믿으면 안 된다.** '플롯 장치'·
  '식사장애'·'유무죄인정'이 전부 사건에 닿는다. **깊이로 자르는 것도 안
  된다** — 진짜 사건인 광주 학생 항일 운동이 5단계, 쓰레기인 바디 스왑도
  5단계다.
- **조직(Q43229)은 뿌리로 쓸 수 없다.** 농민 봉기 → 사회 운동 → 집단 행동
  → 인포멀 그룹 → 단체로 이어져서 민란·시위·군사작전이 전부 조직에도 닿는다.
  뿌리를 늘리면 갈라지는 것이 아니라 겹쳐서, 진짜 사건들이 '둘 다에 닿음'
  으로 보류된다 (보류가 14개에서 54개로 늘었다).
- **매핑표를 사다리 앞에 두면 안 된다.** 제2차 세계 대전의 P31 에 '시대'가
  섞여 있어 시대 노드가 됐다. 앞에 두는 것은 Q5(사람) 하나뿐이다.
- **판정하지 못하면 손대지 않는다.** 11건이 보류로 남았다. 정미의병은
  Wikidata 가 클래스도 시점도 주지 않아 '보복'과 구별되지 않는다. 짐작으로
  옮기면 진짜 사건을 잃는다.

#### 그래프에서의 역할이 Wikidata 의 분류보다 무겁다

사다리의 2·3번이 그것이다. 특히 2번 — **작품이 가리킨 것 말고는 사실층에
닿지 않는 노드는 주제다.** 실측으로 그 자리의 노드 71개가 하나도 빠짐없이
주제어였다. 되돌릴 수 있는 판정이기도 하다: 나중에 그 노드가 연대나 다른
엣지를 얻으면 이 규칙은 더는 걸리지 않고, 7번이 사건으로 되돌린다.

주제끼리 이어져 있어도 주제다. '성 도덕'과 '인간의 성'이 `part_of` 로,
'상실'과 '상실감'이 `related_to` 로 묶여 있었다. 그 엣지 하나 때문에 둘 다
사건으로 남으면 규칙이 무의미해진다. 그래서 '엣지가 없다'가 아니라
**'사실층에 닿지 않는다'** 로 잰다. 닿는 것이 하나라도 있으면 빠지고(그래서
'이춘재 연쇄 살인 사건'은 대한민국과 이어져 있어 사건으로 남는다), 빠진
이웃에 기대던 노드도 따라 빠진다.

#### 속성 경로 질의는 쓰지 않는다

`?c wdt:P279* wd:Q1190554` 는 60개 VALUES 에도 WDQS 가 504 로 거절한다.
타임아웃을 90초로 늘려도 마찬가지다. 대신 **P279 를 한 단계씩 걸어
올라간다** — 같은 크기에서 2.5초에 끝나고, 단계마다 캐시가 남아 다시 돌릴
때 공짜가 된다. 상위로 갈수록 클래스가 합쳐지므로 깊이가 늘어도 질의는
커지지 않는다.

#### 결과

```
노드 77개 재분류 (개념 71 · 인물 4 · 단체 1 · 시대 1) · 보류 11
depicts  157건 → 21건   (전부 실체: 사건 13 · 인물 7 · 단체 1)
about      0건 → 135건
어긋난 엣지 0건
```

인물로 간 4개는 이봉창·윤봉길·이춘재·김헌창이다. **사람이 사건 노드로
앉아 있었다.**

### 작품 명단은 분류에 있다 (`works`)

Wikidata 는 작품 개체는 주지만 역사와 잇는 엣지를 주지 않는다. 한국어
위키백과 분류에서 긁어 온 작품 592편(QID 있는 것)에 대해 재 보면:

| Wikidata 속성 | 592편 중 |
|---|---:|
| P840 서사 장소 | 0 |
| P144 원작 | 0 |
| P921 주제 | 3 |
| P136 장르 | 5 |

**같은 작품들의 분류는 관계를 그대로 말해 준다.**

```
분류:이순신을 소재로 한 작품     → depicts (누구를 다루는가)
분류:조선을 배경으로 한 영화     → set_in  (언제·어디가 배경인가)
분류:조선 역사 드라마            → form    (무슨 매체인가)
```

뿌리 하나(`분류:한국의 역사를 소재로 한 작품`)에서 분류 115개, 문서 599건이
나오고 98%가 QID 를 갖고 있다. `works` 가 이것을 훑어 작품 노드와 엣지를
만든다. **추출 없이** 얻는 엣지다.

`wikipedia.py` 는 "사건 분류는 쓸 수 없다"고 적어 두었다 — 사건 쪽 분류는
'1636년 분쟁' 같은 연도·정비 분류가 대부분이라 그렇다. **작품 쪽은 사정이
다르다.** 같은 위키백과라도 분류의 품질은 주제마다 다르므로, 쓸 수 없다는
경험을 다른 영역까지 넓히지 말 것.

#### 매체를 모르는 작품은 노드로 만들지 않는다

`media` 노드는 `props.form`(영화·드라마·책·만화·게임·무대…) 없이는
만들어지지 않는다 — `Node.__post_init__` 이 막는다. 설명과 달리 이건
나중에 채울 수 있는 값이 아니다. 비어 있으면 화면에서 영화와 드라마가 한
덩어리가 되고, 그 상태를 알아볼 방법도 없다.

판정은 세 단계다: **제목의 괄호 → 분류 이름 → Wikidata P31.** 앞의 것이
더 정확하다 — '(드라마)'는 그 문서가 무엇인지 말하지만, 분류는 그 작품이
어느 묶음에 들어 있는지를 말할 뿐이다.

셋 다 실패하면 만들지 않고 목록으로 보고한다(실측 40건). 이 관문이 junk
필터도 겸한다 — 분류에는 사람(김종학·박유하), 국보, 병풍(봉수당진찬도),
동상(세종대왕 동상), 역사책(발해고)이 섞여 들어온다.

#### 후보가 둘이면 잇지 않는다, 단 이미 하나로 이어 둔 것은 빼고

'허준'·'김유신'·'이상'은 동명이인이 있고 '임진왜란'은 **노드가 둘**이다
(`wd:Q122846639` 차수 102, `wd:Q576338` 차수 14 — 아직 병합되지 않았다).
자동으로 고르면 틀린 곳에 붙으므로 잇지 않는다.

다만 `same_as` 로 **이미 같은 실체라고 이어 둔 후보들은 둘이 아니라
하나다.** '조선'은 `wd:Q28179`(왕조)와 `kr:period:조선`(시대)로 나오는데
`resolve` 가 이미 이어 두었다. 이걸 '후보가 둘'로 세면 조선을 배경으로 한
작품 수백 편이 배경을 잃는다 — 실측으로 배경 엣지가 110건에서 368건으로
늘었다. 대표는 Wikidata 쪽을 쓴다 (QID 가 다른 소스가 붙는 기준이므로).

#### 왕대는 왕조로 물러난다

'분류:조선 세종 시기를 배경으로 한 작품' 같은 왕대 분류가 34개 있다.
왕대 자체는 노드가 아니므로 **왕조로 물러나 잇고, 왕대는 엣지 `label` 에
남긴다** — 나중에 재위 기간으로 연도를 뽑을 때 쓸 근거가 된다.

#### 결과

```
분류 115개 · 문서 599건 (QID 98%)
작품 노드 638개  — 영화 303 · 드라마 298 · 책 31 · 무대 3 · 게임 3
매체 구분(form)  100%
소재(depicts)   183건 · 작품 152편
배경(set_in)    327건 · 작품 302편 (47%)
```

### 인포박스는 소재를 적지 않는다 (`works --harvest`)

"산문 추출보다 인포박스가 빠르지 않나" — 맞는 물음이라 열어 봤다.
작품 틀에는 **소재·배경 칸이 없다.**

```
영화 정보:  제목 장르 감독 제작 각본 출연 음악 배급 개봉 시간 나라 등급
TV 정보:    방송명 장르 방송기간 방송채널 기획 연출 극본 출연자 원작
```

그래도 둘을 준다: **발표일**(연표의 한 축)과 **원작**(작품끼리의 엣지).
감독·출연은 뽑지 않는다 — 역사 그래프가 연예인 그래프가 된다.

**날짜 칸은 순서가 곧 우선순위다.** '제작년도'를 먼저 보면 『한산』이
2020년이 된다. 만든 해와 세상에 나온 해는 다르고, 연표에 서는 것은 나온
해다. 여러 날짜가 적혀 있으면(감독판·재방송·해외개봉) 처음 것을 쓴다.

#### 소재는 도입부의 링크가 말한다

인포박스에 없는 소재는 **도입부 위키링크**에 있다. `[[한산도 대첩]]` 은
QID 로 곧바로 풀리므로 엔티티 해소가 필요 없다 — `infobox.py` 가 쓰는
것과 같은 성질이다. 다만 링크를 그냥 받으면 안 된다:

```
관문 없이 인트로 링크를 다 받으면   인물 39 · 장소 19 · 정체 5 · 사건 4
그 인물 39명의 정체                김지운 임권택 하희라 이준익 신현준 …
```

**절반 이상이 감독과 배우다.** 관문이 셋 필요했다.

1. **단서 어구.** 링크 뒤 45자 안에 '소재로'·'다룬'·'그린'·'모티브'·
   '주인공으로' 같은 말이 있어야 한다.
2. **만든 사람 걸러내기.** 링크와 단서 사이에 '소설'·'원작'·'연출' 같은
   말이 끼면 버린다 — `[[선우휘]]의 소설을 바탕으로` 에서 선우휘는
   원작자이지 다뤄진 인물이 아니다. 몰년 관문은 이미 죽은 작가를 못 막는다.
3. **몰년.** 사람은 죽은 뒤라야 소재가 된다. 몰년이 없으면 잇지 않는다 —
   살아 있는 사람이 작품에 얽혀 있다면 만든 쪽일 가능성이 압도적이다.
   작품 발표일을 아는 경우 몰년이 그보다 앞서는지도 본다.

**장소는 소재가 아니라 배경이다.** 『군함도』가 나가사키를, 『대호』가
지리산을 '다루는' 것이 아니라 거기를 배경으로 한다. 도착이 장소면
`set_in` 으로 잇는다.

#### 단서는 도입부에만 있다

본문 전체(줄거리·역사적 사실)까지 넓혀 봤지만 **한 건도 늘지 않았다**
(작품 80편 기준 도입부 37개, 본문 전체 37개). 줄거리는 관계를 단서 어구
없이 적는다 — "측천무후는 황제 즉위 후…", "고선지가 잠시 어린이로
등장한다". 규칙으로 캘 수 있는 것은 여기까지고, 그 다음은 산문 추출이다.

#### 결과

```
작품 문서 658건을 읽어
  발표일   109 → 382편
  원작(adapted_from)   12건
  소재(depicts)  184 → 284건
  배경(set_in)   327 → 345건
표본 30건 정밀도 30/30
```

#### 배우 이름은 넣기 전에 지운다 (`enrich`)

작품 문서의 '등장 인물' 절은 배역과 배우가 뒤섞인 목록이다. 그대로
추출에 넣으면 배우가 역사 인물로 승격된다 — README 의 "족보 목록은
모델을 망가뜨린다"와 같은 함정이고 처방도 같다. `enrich` 가 작품 산문을
저장할 때 그 절과 하위 절을 통째로 걷어낸다(시청률·수상·각주도 함께).
**'역사적 사실'·'역사와 다른 점' 절은 남긴다** — 작품이 무엇을 다루는지,
어디가 고증과 다른지를 그 절이 말한다.

실측: 『대조영』 9,905자 → 1,469자. 배우 이름은 사라지고 '역사적 사실'과
'역사와 다른 점'만 남는다. 그 1,469자가 측천무후·대무예·고선지·설인귀·
걸걸중상을 말한다.

### 두 개의 섬 — 엔티티 해소

국가유산청 그래프와 Wikidata 그래프는 기본적으로 서로 닿지 않는다.
숭례문에서 세종으로 가는 경로가 없으면 온톨로지 그래프로서 작동하지 않는다.

접합점은 **장소와 시대**다. 국가유산청은 유물마다 시도·시군구(`ccbaCtcdNm`,
`ccsiName`)와 시대(`ccceName`)를 주고, Wikidata 는 같은 지명과 왕조를
항목으로 갖고 있다. `resolve` 가 이 둘을 `same_as` 로 잇는다.

- 시대: 매핑표 기반 (조선시대 → `wd:Q28179`), score 1.0
- 장소: 정규화 후 정확 일치 (`서울특별시` → `서울`), score 0.9.
  후보가 둘 이상이면 잇지 않는다 — 자동으로 고르면 틀린 곳에 붙는다.

`resolve` 는 끝에 **연결 검증**을 출력한다. `same_as` 행 수만 세면
"연결된 것 같다"는 착각을 하기 쉬우므로, 소스를 건너뛰는 링크 수와
국가유산청 노드에서 Wikidata 로 실제로 나가는 경로 수를 함께 센다.

### 활용신청이 필요하다

두 포털 모두 **키가 유효해도 데이터셋마다 따로 신청**해야 한다.

- data.go.kr → `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` (코드 30)
- culture.go.kr → `{"message":"Unauthorized","http_status_code":401}`

`doctor` 가 이 상태를 데이터셋별로 진단한다. 승인 후 `datagokr.py` /
`culture.py` 의 `CANDIDATES` 에 실제 엔드포인트 경로를 채우면 된다
(현재 등록된 경로는 미검증 추정값이라 `[12] 존재하지 않는 서비스`가 난다).

## 실측으로 알아낸 API 함정

- **국가유산청 상세 조회**는 목록이 주는 **13자리** `ccbaAsno` 를 그대로
  써야 한다. 8·10자리로 자르면 에러가 아니라 **HTTP 200 에 빈 필드**가
  돌아와 조용히 실패한다.
- **왕조 QID 를 추측하면 반드시 틀린다.** Q34049 는 고려가 아니라 셈어파,
  Q28194 는 고구려가 아니라 독일 가수다. `doctor` 가 기대 라벨과 대조해
  검증한다.
- **WDQS 는 60초 제한**이 있다. 정체 9개를 `VALUES` 로 묶고 label service 를
  붙이면 타임아웃난다. 정체별로 쪼개고 라벨은 별도 배치로 조회한다.
- **WDQS 는 과호출에 403/429/502** 로 응답한다. 요청 간격 1.5초 이상 권장.
- **공공 API 는 인증 실패도 HTTP 200 으로 준다.** 본문의 `errMsg` 를 봐야
  한다.

### 별칭은 있는데 화면까지 오지 않았다

연표에 한일병합은 섰는데 **'경술국치'로는 아무것도 찾을 수 없었다.**
두 가지가 겹쳐 있었다.

```
전체 그래프의 별칭   5,064건
조선 그래프의 별칭       0건      ← scope 가 aliases 표를 안 옮겼다
```

**`scope` 가 별칭을 안 옮기고 있었다.** 노드·엣지·`same_as` 는 옮기면서
`aliases` 만 빠져 있었다. 화면이 읽는 것은 시대 그래프이므로, 별칭 검색이
**화면에서는 한 번도 동작한 적이 없다** — '이방원'으로 태종을 찾는 것도
전체 그래프에서만 되던 일이었다.

**`wikidata.fetch_aliases` 는 쓰이지 않는 코드였다.** 함수는 있는데
파이프라인 어디에서도 부르지 않았다. 그래서 5,064건은 전부
국가유산청·위키백과가 노드에 얹어 준 것이고, Wikidata 가 들고 있는 한국어
별칭은 하나도 없었다 — 한일병합에는 경술국치·국권피탈·일제강점을 비롯해
13개가 적혀 있다. `histgraph aliases` 가 그걸 가져온다(사건·조직·장소·
직위·매체 2,244개에서 2,184건).

인물 28,961명은 기본에서 뺐다 — 배치가 145회라 따로 돌린다
(`aliases --types person`).

### 사건이 자기 쪽에 적어 둔 관계 (`links`)

연표에 `왕자의 난`(1398~1400)·`제1차 왕자의 난`(1398)·`제2차 왕자의
난`(1400)이 나란히 섰지만, **셋 사이에는 엣지가 하나도 없었다.** '왕자의
난'의 연결은 0건이었다 — 연표에서 나란히 서니 이어져 보였을 뿐이다.

**관계를 인물의 속성으로만 긁고 있었다.** 수집이 물어본 것은 인물↔사건
(P1344 '참여') 하나뿐이다. 그래서 사건이 자기 문서에 적어 둔 것은 통째로
빠져 있었다 — 전수조사로 여섯 갈래가 나왔다.

| 속성 | 뜻 | 우리 엣지 | 전체 / 조선 |
|---|---|---|---|
| P361 `~의 일부` / P527 `~로 이루어짐` | 상하위 | `part_of` | 77 / 63 |
| P710 `참가자` | 사건이 적어 둔 참가자 | `participated_in` | 193 / 134 |
| P276 `장소` | 발생 장소 | `occurred_at` | 32 / 3 |
| P155 `이전` / P156 `다음` | 전후 | `related_to` ('다음') | 28 / 17 |
| P828 `원인` / P1542 `결과` | 인과 | `related_to` ('원인') | 16 / 4 |

`histgraph links` 가 이 여섯을 한 번에 가져온다. 실측으로 드러난 것:

- **옥포 해전에 이순신이 없었다.** 사건 쪽 참가자(P710) 를 안 물어봐서
  이순신·도도 다카토라·도요토미 정권이 모두 끊겨 있었다. 신임사화도
  노론·소론과 이어져 있지 않았다.
- **원인·결과 엣지가 그래프 전체에 한 건도 없었다.** 병인박해→병인양요,
  제너럴셔먼호 사건→신미양요, 한일신협약→대한제국 군대해산→남대문 전투가
  모두 끊긴 채였다. 한국사 서술의 뼈대가 통째로 없었던 셈이다.
- 사화↔무오·갑자·기묘·을사사화, 임진왜란↔칠천량 해전·북관대첩 등 전투
  30여 건, 정묘호란→병자호란.

- **Wikidata 는 같은 사실을 양쪽에 적는다.** 제1차는 P361 로 '왕자의 난의
  일부'라 하고, 왕자의 난은 P527 로 '제1차로 이루어짐'이라 한다. 그대로
  담으면 방향만 다른 엣지가 둘 생기므로 한 방향으로 모은다 — 하위에서
  상위로, 앞선 사건에서 뒤 사건으로.
- **없는 사건을 새로 만들지 않는다.** 반대쪽 끝이 그래프에 없는 관계
  1,496건은 건너뛰고 수만 보고한다. 여기서 노드를 만들기 시작하면 교황청
  콘클라베처럼 한국사와 무관한 사건이 딸려 들어온다.
- **양끝 타입이 스키마에 맞아야 담는다.** Wikidata 는 옥포 해전의 참가자로
  이순신과 '일본'을 나란히 적는데, 우리 그래프에서 일본은 place 라 '장소가
  해전에 참여했다'가 된다. 온톨로지가 막아 주는 것을 버리고(46건) 몇
  건인지 보고한다.
- **이름이 같은 두 노드는 잇지 않는다.** Wikidata 는 임진왜란을
  1592~1593년 침입(Q122846639)과 1592~1598년 전쟁(Q576338) 둘로 두고
  앞의 것을 뒤의 것의 일부로 적는데, 우리 그래프는 둘 다 라벨이
  '임진왜란'이라 화면에 "임진왜란은 임진왜란의 일부다"가 뜬다. 사실은
  맞지만 읽을 수 없는 문장이고, 이을 일이 아니라 **합칠** 일이다.
  `relabel` 의 중복 보고와 같은 자리에 남긴다.

### 고립 사건 전수조사 — 화면의 '관계 없음'은 어디서 오나

'왕자의 난'이 홀로 서 있던 것이 하나짜리 사고였는지 확인하려고 조선
그래프의 사건 385개를 전수조사했다. **엣지가 하나도 없는 사건이 19개,
시간 엣지만 있어 화면에 '연결된 관계가 없습니다'로 뜨는 사건이 8개**
였다 — 나주괘서사건·무고의 옥·문체반정·병오박해·신해박해·여권통문·
대한제국 군대해산 …

원인은 셋이었고 셋 다 '안 물어본 것'이었다.

1. **사건 쪽 속성을 안 물어봤다** — 위의 `links` 여섯 갈래.
2. **같은 사실이 소스에 따라 다른 자리에 있었다.** 위키백과에서 온 사건은
   `from_period` 엣지로 조선에 붙는데 Wikidata 에서 온 사건은
   `props.polity` 칸에만 있었다(전체 198건 · 조선 105건). 화면이 읽는 것은
   엣지다. `resolve` 가 이제 그 칸을 엣지로 세운다.
3. **재시도가 질문을 바꿔치기했다** (`http.py`) — 아래.

결과: 조선 그래프에서 **엣지가 하나도 없는 사건 0개**. 시간 엣지만 있는
사건 22개가 남았는데, 이건 Wikidata 에도 관계가 없는 것들이라 산문
추출(`extract`)이 할 일이다.

이름 가족(`제N차 X` ↔ `X`)도 함께 훑었다. 남은 어긋남 4건은 전부 승격되지
않은 추출 고아(`ex:`)다 — 제1·2차 요동 정벌, 제1차 진주성 전투. 노드가
둘로 갈린 것이라 이을 일이 아니라 합칠 일이다.

### 재시도가 질문을 바꿔치기했다 (`http.py`)

전수조사 중에 `links` 를 두 번 돌렸더니 두 번째에 관계 22건이 더 들어왔다.
같은 질문에 답이 달라진 것이다.

`_fetch` 의 HTTPError 처리가 응답 본문을 `body` 변수에 담고 있었는데, 그
`body` 는 **다음 재시도에 보낼 요청 본문**이었다.

```python
except urllib.error.HTTPError as err:
    body = err.read()...      # ← 요청 본문을 오류 HTML 로 덮어쓴다
```

WDQS 가 503 을 한 번 뱉으면 다음 시도는 SPARQL 대신 오류 HTML 을 POST
한다. 그 응답은 원래 질문의 캐시 자리에 들어앉는다. 한 구간(150개 QID)이
통째로 비었고 사건 관계 98건이 조용히 사라졌다 — POST 를 쓰는 모든
SPARQL 수집에 해당한다. 회귀 테스트로 고정했다.

### 연도만 아는 날이 1월 1일 행세를 하고 있었다 (`precision`)

Wikidata 에서 '1592년'은 `1592-01-01T00:00:00Z` 로 온다. 몇 자리까지 아는
값인지(`wikibase:timePrecision`, 9=연 10=월 11=일)는 **값이 아니라 문장에**
붙어 있는데, `wdt:` 로 긁는 우리 수집은 값만 가져왔다. 그래서 DB 에는
연도만 아는 날이 전부 1월 1일로 앉아 있었다 — 전체 그래프에서 시작일이
1월 1일인 노드 7,117개.

**연표가 몰린 해를 늘려 세우기 전에는 티가 안 났다.** 늘려 세우고 나니
한 해 안의 차례가 곧 시간 순으로 읽히는데, 지어낸 1월 1일이 4월의 동래성
전투보다 앞에 서면 없는 날짜로 순서를 말한 것이 된다. 반대로 날짜만 보고
잘라낼 수도 없다 — 3·1 운동(1919-03-01)은 진짜 3월 1일이다. 갈리는 것은
날짜가 아니라 자릿수이므로, 문장에 물어봐야 한다.

`histgraph precision` 이 `p:`/`psv:` 로 문장의 값 마디까지 내려가 자릿수를
읽고, 그만큼 잘라 부분 날짜로 되돌린다 — `1592`, `1592-09`. 스키마는
처음부터 부분 날짜를 허용하고(`ontology.Node`), 연도를 읽는 쪽은 전부 앞
네 자리만 보므로 나머지 파이프라인은 그대로다. 실측: 조선~일제강점기
그래프에서 3,452건, 전체 그래프에서 7,512건.

- **후보는 날이 01 인 값뿐이다.** 다른 날짜는 이미 일 단위로 아는 값이다.
- **같은 날짜가 여러 문장에 다른 자릿수로 적혀 있으면 정밀한 쪽을 남긴다.**
  선조(Q484359)는 생년을 1552-11-21(일)과 1552-01-01(연) 둘로 갖고 있다.
- 화면은 늘어난 해의 첫 줄에만 해를 적고 나머지 줄에는 달을 적는다. 달을
  모르는 줄은 **비운다** — 빈 칸이 '1월'이 아니라 '모른다'는 뜻이다.
- 수집 뒤에 다시 돌릴 것 (`upsert_nodes` 가 날짜 칸을 덮어쓴다).

### 왕의 재위는 노드가 아니라 엣지에 있다 (`reigns`)

연표는 사건을 세워 놓고 **누구 때의 일인지**는 말하지 못했다. 그래프에
임금도 있고 '조선 임금' 자리도 있는데, 둘을 잇는 `held_position` 엣지
552개가 **전부 날짜 없음**이었다.

재위는 인물의 값도(그건 생몰이다) 직위의 값도 아니다. '언제부터 언제까지
그 자리에 있었나'는 **그 둘을 잇는 엣지의 성질**이고, Wikidata 도 그렇게
적는다 — P39 문장의 한정어(`pq:P580`/`pq:P582`). 우리 수집은 `wdt:` 로만
긁어서 한정어에 닿은 적이 없었다.

`histgraph reigns` 가 그걸 옮겨 적는다. 전체 그래프에서 재위를 아는 임금
45명(고구려 동명성왕부터 대한제국 고종까지), 조선 그래프에서 26명.

- **군주 자리 목록을 코드에 박지 않는다.** 조선은 '조선 임금'(Q22304810)
  이라는 전용 항목을 쓰지만 고려 임금들은 일반 항목인 '군주'(Q116)·
  '왕(王)'(Q12087706)에 걸려 있다. 박아 두면 고려가 통째로 빠진다.
  계층(`P279*`)에 물어본다.
- **왕비는 갈라낸다.** '조선 왕비'도 `P279*` 로 군주에 닿는다(왕비 → 여왕
  → …). 그대로 두면 왕비 35명이 왕과 같은 띠에 선다.
- **추존왕은 재위가 없다.** 원종은 '조선 임금' 자리를 갖고 있지만 한정어가
  비어 있다 — 앉은 적이 없기 때문이다. 없는 것을 0년으로 채우지 않는다.
- **사망은 재위의 끝이 아니다.** 태조는 1398년에 물러나 1408년에 죽었고,
  고종은 1907년에 물러나 1919년에 죽었다. 둘을 한 점으로 합치면 상왕으로
  산 10년이 사라진다. 그래서 화면은 재위를 막대로, 몰년을 동그라미로
  따로 찍고 그 사이를 점선으로 잇는다.
- 다시 수집해도 날짜는 지워지지 않는다 (`upsert_edges` 의 ON CONFLICT 는
  날짜 칸을 갱신하지 않는다). 다만 `props` 는 덮어쓰므로 재위 표식이
  날아간다 — 수집 뒤에 다시 돌릴 것.

화면에서는 연표 왼쪽에 **왕의 재위 띠**가 선다. 사건을 고르면 그 사건이
누구 때인지 막대가 밝아진다 — 갑자사화(1504)를 고르면 연산군이 밝아진다.
조선의 시간을 사람은 절대 연도가 아니라 임금으로 읽기 때문이다.

**대통령도 같은 띠에 선다** (2026-09-04). 1948년 뒤의 시간도 같은 방식으로
읽힌다 — '1979년'보다 '박정희 말년'이 먼저 온다. 이승만부터 이재명까지
14명이 왕과 같은 줄, 같은 모양(막대 = 재임, 동그라미 = 몰년)으로 서고,
말만 재위/재임으로 갈린다. 표식 `props.reign` 의 값이 자리의 종류
(`monarch`·`president`)다.

- **자리는 계층으로 찾되 조건이 둘 더 있다.** '대통령'(Q30461)의 하위
  가운데 관할(P1001)이 대한민국인 자리만, 그리고 권한대행(Q4676846) 계열은
  뺀다. 뿌리 '대통령' 자체에는 세계의 대통령 6,285명이 걸려 있고, 그래프의
  직위 엣지에는 '조선민주주의인민공화국 주석'도 계층으로 대통령에 닿는다.
- **표식 없는 대행은 겹침으로 가른다.** 황교안은 Wikidata 에 '대한민국
  대통령' 2016-12-09~2017-05-10 으로 적혀 있고 대행 표식이 없다. 그 시작이
  박근혜의 임기(~2017-03-10) 한가운데다 — 한 자리에 둘이 동시에 앉을 수는
  없으니 남의 임기 안에서 시작하는 쪽이 대행이다(`drop_nested_terms`).
  같은 날 넘겨받는 것(박정희 사망일에 최규하)은 겹침이 아니다. 이 규칙은
  **대통령 자리에만** 건다 — 군주 자리는 '왕'·'여왕' 같은 일반 항목이라
  여러 나라의 임금이 한 자리를 나눠 쓰고, 겹침이 곧 정상이다 (실측: 걸면
  고려 우왕·진덕여왕이 빠졌다).
- **재임 중은 끝이 없다.** 끝을 모르는 것과 아직 안 끝난 것은 다르다 —
  살아 있고 끝 날짜가 없으면 오늘까지 긋고 `ongoing` 으로 밝힌다. 화면은
  `2025~` 로만 적는다. 죽은 사람의 빈 끝은 전처럼 몰년으로 닫는다.

### 참여는 편을 말하지 않는다 — 말뭉치와 역할 판정 (`corpus`·`ask`·`roles`)

화면이 **"이재명은 12.3 내란에 참여했다"** 고 말했다. 그는 체포 명단에
오른 사람이다. 엣지는 인포박스의 `주요인물2` 에서 왔다 — 인포박스는
사건의 양편을 `주요인물1`(계엄을 편 쪽: 윤석열·김용현)과 `주요인물2`
(막은 쪽: 우원식·이재명·한동훈)로 나눠 적는데, 파서가 편을 버리고 둘 다
`participated_in` 으로 만들었고 화면은 그것을 '참여'로 읽었다.

두 겹으로 고쳤다.

1. **인포박스는 '참여'라고 말한 적이 없다.** 칸 이름을 엣지 라벨로 남기고
   (지휘관·주요 인물·교전·가해) 편 번호를 `props.side` 에 적는다. 화면은
   라벨대로 읽는다 — "…의 주요 인물이다". 어느 편이 무엇을 했는지는
   여전히 모른다. 그것은 구조에 없고 **산문**에 있다.
2. **산문을 말뭉치로 두고 근거를 찾는다.** `corpus` 가 1945년 뒤 사건과 그
   이웃(인물·단체)의 위키백과 본문 **전체**를 내려받아 문단으로 쪼개
   `data/corpus.sqlite` 에 넣고 FTS5(trigram)로 색인한다. `ask "체포 명단"`
   이 그 문단을 찾는다. `roles` 는 사건으로 들어가는 인물의 `participated_in`
   마다 **그 사람이 나오는 문단만** 모아 모델에 묻는다: 주도·가담·대항
   (참여) / 피해·표적·수습·언급 (참여가 아님). 답의 근거 구절이 준 문단에
   실제로 있어야 받는다 (`extract.evidence_supported` 와 같은 관문). 참여가
   아닌 역할과 근거 없는 엣지는 `related_to` 로 옮기고 `props.was` 에 원래
   타입을 남긴다. 화면은 역할과 근거 문장을 함께 보여준다 — "이재명은 12.3
   내란에서 표적이 되었다" 아래 「체포 명단을 불러주며 …」.

말뭉치가 그래프 파일과 따로인 이유: 글은 그래프보다 훨씬 크고, 화면
DB(`korea.sqlite`)는 저장소에 실려 배포된다. `*.sqlite` 는 .gitignore 가
막으므로 말뭉치는 각자 내려받는다 (`histgraph corpus`, 800건 남짓에 10분).

검색이 trigram 인 이유: 한국어는 조사·어미가 붙어 '이재명은'과 '이재명'이
단어 토크나이저에서 다른 말이다. 세 글자씩 자르면 그 문제가 없고, 대신
두 글자 질의는 LIKE 로 물러난다.

**모델은 근거를 찾는 데만 쓴다.** 관계를 만들지 않는다 — 이미 있는 엣지에
역할과 인용문을 붙일 뿐이고, 인용이 문단에 없으면 버린다. 이 규칙 덕에
모델이 틀려도 화면에는 '문단에 있는 문장'만 뜬다.

### 영어로 뜨는 노드 (`relabel`)

조선 그래프에서 '왕자의 난'을 따라가면 **`Sayuksin assassination plot`**
이 나왔다. 한국사 그래프인데 이름이 영어다.

수집 쿼리는 라벨을 `"ko,en"` 으로 물어본다. 한국어 라벨이 없으면 영어가
오고, 그게 그대로 노드 이름이 된다.

```
전체 그래프의 영문 노드   1,490개   (인물 1,209 · 직위 98 · 사건 72 · …)
조선 그래프의 영문 노드      32개   ← 화면이 읽는 것은 이쪽
```

**다시 수집해도 안 고쳐진다.** 그 1,480개(wd 소스)를 상대로
`rdfs:label(ko)`·`skos:altLabel(ko)`·한국어 위키백과 사이트링크를 전부 다시
물어봤더니 새로 한글 이름을 얻을 수 있는 건 **2개**뿐이었다. 나머지는
Wikidata 에 한국어 이름이 아예 없다.

그래서 이름을 손으로 적은 표(`data/ko_labels.tsv`, 435개)를 두고
`relabel` 이 덮어쓴다. 표에는 근거 칸이 있다 — 그 이름이 어디서 나왔는지
(`ja=趙秉昌`, `zh=金喆煥`, `로마자 Kim Won-ju`) 적어 두고, 의심스러우면
그 칸부터 본다. 한국·중국 인물의 한자는 한국 한자음으로 읽고
(趙秉昌→조병창), 일본 인물·지명은 일본어 발음을 음역한다
(加藤清忠→가토 기요타다).

**바꾼 이름이 중복을 드러낸다.** `Cho Sok` 을 조속으로 고치자 1595~1668년
생몰이 같은 `조속` 노드가 이미 있었다. 이정보·남병길·미마지도 그랬다 —
Wikidata 에 같은 인물이 두 항목으로 있는 것이다. `relabel` 은 이걸
**보고만 하고 합치지 않는다**; 합치는 규칙은 `promote` 쪽에 있다.

**남은 1,055개는 적지 않았다.** 대부분 한자 없이 로마자 표기만 있는
근현대 남북한 인물이라(`Pak Chung-il`) 음절 복원이 갈린다. 근거 없이 적는
대신 `relabel` 이 끝날 때마다 남은 수를 찍는다. 화면이 읽는 그래프는
0개다.

**그런데도 세 번 떴다.** 표가 없어서가 아니라 안 돌려서였다 — 그래프를
다시 만들고 `relabel` 을 잊거나, 원본에는 돌리고 파생본에는 안 돌렸다.
2026-09-04 세 번째(`1923 Jogono Police Station bombing`) 뒤로는 사람이
기억하지 않는다: `scope` 가 파생본에 바로 돌리고 남으면 실패하며,
`tools/check_korean.py` 가 push 전(훅)과 push 뒤(CI)에 배포될 DB 를 센다.
라벨·설명에 한글이 한 자도 없으면 걸린다 (`labels.foreign_text`).

### 영어로 뜨는 설명 (`redescribe`)

이름을 한국어로 바꿔 놔도 **설명이 영어로 떴다.** 임진왜란을 누르면
`1592-1593 invasion of Joseon by Japan Toyotomi government` 가 나왔다.

한국어 위키백과 문서가 없는 노드를 Wikidata 한 줄 설명으로 채우는 경로
하나에서만 들어온다. 실측 2,222건이었고, 그게 **한글이 한 자도 없는 설명
전부**였다.

```
서로 다른 문구            881개
국적·괄호를 걷어내면      643개   ← 상위 100개가 절반을 덮는다
```

산문이 아니라 '(국적) (직업)' 꼴의 딱지다. 그래서 번역기가 아니라
**사전과 규칙**으로 옮긴다(`src/histgraph/koreanize.py`). 번역기는 답이
옳은지 확인할 방법이 없고 틀리면 조용히 틀린다. 사전은 무엇을 무엇으로
옮겼는지 한 줄씩 읽을 수 있고, **모르는 말은 모른다고 말한다.**

```
histgraph.sqlite   옮김 1,913건 (86%) · 비움 309건
joseon.sqlite      옮김    45건       · 비움  27건
```

`Joseon civil servant (1390 - 1453)` → `조선의 문신 (1390~1453)`.
같은 낱말도 시대에 따라 가른다 — `civil servant` 가 조선에서는 문신,
대한민국에서는 공무원이다. 관직은 품계와 기관을 살린다
(`second rank official in Uijeongbu during the Joseon Dynasty` →
`조선의 의정부 2품 관직`). 정/종은 원문이 구분해 주지 않으므로 적지
않는다 — **모르는 것을 아는 척하느니 덜 말하는 쪽이 낫다.**

**비운 309건은 실패가 아니라 지어내지 않았다는 기록이다.**
`Ph.D. University of Wisconsin-Madison 1982` 같은 1건짜리 자유 서술이
320개였다. 화면은 `설명 없음 — 한국어로 옮길 수 있는 설명이 아직
없습니다` 라고 적는다. 틀린 한국어 한 줄보다 빈 칸이 낫다.

원문은 `props.desc_en` 에 남는다. 사전에 말을 더하고 다시 돌리면 비워
뒀던 설명이 되살아난다 — 실제로 조선 관직·전투 규칙을 나중에 더해 14건을
되살렸다. 이것이 사전을 키우는 정상적인 방법이다.

**다시 들어오는 것은 관문 하나로 막는다.** `ontology.Node.__post_init__`
에서 한글 없는 설명을 옮기거나 비운다. 모든 커넥터가 `Node` 를 지나므로
커넥터마다 검사를 적지 않는다. **예외가 하나 있다** —
`wikipedia._fill_from_wikidata` 는 `Node` 를 거치지 않고 SQL 로 직접
쓰므로 거기에 같은 규칙을 한 번 더 적어 뒀다. SQL 로 설명을 쓰는 경로를
새로 만들면 거기에도 걸어야 한다.

### 물어보고 답을 버리면 없는 것이 된다 (사건의 정체)

연표에 **경술국치가 없어서** 따라가 봤다. 전체 그래프에는 한일병합
(`wd:Q3277083`)이 1910-08-29 로 정확히 들어와 있는데 조선 그래프에는
없었다. 같은 이유로 빠진 사건이 조선 연대(1392~1910) 안에만 94건이었다 —
진주민란·갑오개혁·신임사화·경신 대기근, 그리고 임진왜란 전투 30여 건.

`fetch_events` 의 쿼리는 이렇게 생겼다.

```sparql
?e wdt:P31/wdt:P279* ?cls ; wdt:P17 wd:{polity} .
```

**정체를 물어 놓고 답을 버리고 있었다.** 인물은 처음부터 `props.polity` 를
적어서 `scope.select_seeds` 가 그걸로 씨앗을 고르는데, 사건에는 그 칸이
비어 있었다. 그래서 사건은 `props.seed_era`(위키백과 시드 목록에 손으로
적은 것)나 왕조 노드와의 직접 연결이 있는 것만 살아남았다.

빠진 94건의 P17 실측: **조선 73 · 대한제국 14** · 그밖 5(교황령 conclave
셋·일본 제국·청나라) · P17 없음 2.

세 가지를 고쳤다.

- `fetch_events` 가 `props.polity` 를 적는다. 이미 쌓인 노드는
  `tools/backfill_event_polity.py` 가 `json_set` 으로 그 칸만 채운다 —
  **다시 수집하면 안 된다.** `upsert_nodes` 가 `props = excluded.props` 로
  통째로 덮어써서 `enrich`(kowiki_url)와 `promote`(merged_from)가 나중에
  채운 값이 날아간다.
- **후계 정체의 사건도 담는다.** 조선은 1897년에 대한제국이 되고 1910년에
  끝나는데, Wikidata 는 경술국치·을사조약·군대해산의 P17 을 대한제국으로
  적는다. 1897년에서 자르면 '조선이 어떻게 끝났나'가 통째로 빠진다.
  `Era.successor_events` 로 **사건에만** 적용한다 — 대한제국 국적 인물까지
  씨앗으로 삼으면 근현대로 끌려간다(전체 인물의 65%가 대한민국이다).
- **연대를 아는 사건은 엣지가 없어도 남긴다.** 한일병합 노드는 엣지가 0개라
  `scope` 의 고립 노드 정리에 걸려 있었다. 고립을 버리는 이유는 화면에
  점으로만 뜨기 때문인데, 연표에서는 '언제'라는 값 하나로 제 몫을 한다.

결과: 조선 그래프의 사건 297 → **385개**, 그중 연대를 아는 것 76 → **160개**.

### 안 물어본 것은 없는 것이 된다 (`spans`)

인물은 P569/P570(생몰), 사건은 P580/P582/P585(시작·종료·시점)를 처음부터
가져왔는데 **조직에는 날짜를 한 번도 물어본 적이 없었다.** 조직은 다른
노드의 엣지 상대(국적·직위·소속)로만 들어와서 라벨과 URL 뿐이었다.

```
조선 그래프의 org 80개  →  날짜 있는 것 0개
그중에 이 그래프의 중심인 조선(wd:Q28179) 이 있었다
Wikidata 에는 P571=1392-08-13 · P576=1897-10-12 로 적혀 있다
```

화면에서 조선을 골랐을 때 연표가 '연도 미상'이라고 말한 것이 이 구멍을
드러냈다. 없는 데이터가 아니라 **안 물어본 데이터**였다.

`uv run histgraph --db data/joseon.sqlite spans` 이 P571/P576 을
채운다(없으면 P580/P582 로 물러난다). 조선 그래프 80개 중 33개, 전체
그래프 342개 중 158개가 채워졌다 — 나머지는 Wikidata 에도 없다.
**이미 적혀 있는 날짜는 건드리지 않는다.** 채우기만 한다.

## 산문의 종류가 결과를 좌우한다

"산문에서 추출하면 된다"는 말은 절반만 맞다. **어떤 산문인지가 중요하다.**

국가유산청 `content` 2,903건을 표지어로 훑어본 결과:

| 구분 | 문서 수 | 비율 |
|---|---|---|
| 인물 표지 있음 | 1,538 | 53% |
| 사건 표지 있음 | 1,099 | 38% |
| **둘 다 있음** | **634** | **22%** |
| 서지·규격 기술 | 788 | 27% |

가장 긴 문서(5,023자)를 열어보면 이렇다:

> 상하단변(上下單邊), 좌우쌍변(左右雙邊)에 반곽(半郭) 24.5×15.8cm, 무계(無界)이며,
> 반엽의 행자수는 17행 34자, 판심에는 '진 제오십일(晋第五十一)'…

**유물 해설문은 "이 물건이 무엇인가"를 적은 글이다.** 우리가 필요한 건
"누가 무엇을 했는가"다. 길이순으로 문서를 고르면 가장 긴 문서가 판본
치수 나열이라 API 비용이 그대로 헛돈다.

그래서 두 가지를 했다.

**1. 서사 점수로 문서를 선별한다** (`extract --min-score`). 인물·사건
표지에 가점, 서지·규격 표지에 감점. 길이는 약한 보정으로만 쓴다.

```
전체 2,903건 → min-score 1.0: 1,745건 → min-score 2.0: 619건
```

**2. 진짜 서사 코퍼스를 붙였다** (`enrich`). 실록과 백과사전은 활용신청
대기 중이라, 지금 막힘 없이 쓸 수 있는 건 한국어 위키백과뿐이다.

비교해보면 차이가 분명하다:

| 출처 | 예시 |
|---|---|
| 국가유산청 | `반곽 24.5×15.8cm, 무계이며 행자수는 17행 34자` |
| 위키백과 | `박정희는 … 1979년 10·26 사건 당시 김재규 전 중앙정보부장의 총격으로 서거하였다` |

## 위키백과 보강 (`enrich`)

새 노드를 만들지 않는다. Wikidata 항목에 달린 한국어 위키백과
**sitelink** 를 따라가 기존 노드의 `description` 을 채운다. 새로 만들면
엔티티 해소를 또 해야 하지만, sitelink 는 QID 가 곧 키라서 정확히 같은
노드에 꽂힌다.

- 노드 라벨을 문서명으로 쓰면 안 된다 — 우리 라벨은 `조선 세종`인데
  실제 문서명은 `세종`이라 조회가 빗나간다.
- 인증키 불필요. 단 **User-Agent 는 필수** — 없으면 Wikimedia 가
  JSON 대신 오류 HTML 을 돌려준다.
- 도입부는 한 요청에 20건(인물 항목 기준 900~1,400자), `--full` 은
  본문 전체지만 요청당 1건이다.

### 화면의 빈 설명칸은 자료가 없어서가 아니었다

조선 그래프의 `사량진왜변` 에 설명이 없었다. 위키백과에 문서가 멀쩡히
있는데도 비어 있었고, 원인은 셋이었다.

**1. 차수 상위 N개만 받았다.** 기본값이 `--limit 500` 이라 차수 1짜리
노드는 순번이 오지 않았다. 설명이 있는 인물의 평균 차수는 8.4, 없는
인물은 2.1 이다 — 빠진 것은 '자료가 없는 노드'가 아니라 '순번이 오지
않은 노드'였다. `--limit` 의 기본값을 없앴다(기본은 남은 전부). 차수
정렬은 남긴다 — 중간에 끊어도 많이 연결된 것부터 채워지는 편이 낫다.

**2. `person`·`event` 만 대상이었다.** 장소 350·단체 77·직위 33개는
한 번도 조회된 적이 없다. 기본 타입을 wd 노드 전체로 넓혔다.

**3. 넘겨주기 문서를 통째로 버렸다.** `redirects=1` 이라 응답의 문서명이
요청한 것과 다르게 온다(`신숙공주` → `순숙공주`). 그런데 결과를 요청한
이름으로만 찾고 있어서, 넘겨주기가 걸린 문서는 본문을 받아놓고도 버려졌다.

```
조선 그래프 wd 노드의 빈 설명   2,796 → 27   (3,832개 중 99.3% 채움)
그 중 넘겨주기로 되찾은 것            4
```

**못 채운 것을 못 채웠다고 적는다.** 남은 27개는 한국어 위키백과에 문서가
없고 Wikidata 한 줄 설명도 없는 노드다. 문서가 없는 노드에는
`props.no_kowiki` 를 찍어 다음 실행이 같은 헛수고를 반복하지 않게 한다
(`--refresh` 는 그 표시도 무시하고 다시 본다).

**단, 쿼리가 죽은 것과 문서가 없는 것을 섞으면 안 된다.** sitelink 조회는
공개 엔드포인트라 502·429 로 곧잘 죽는다. 실패한 구간의 QID 까지
`no_kowiki` 로 못 박으면 타임아웃 한 번에 200개가 영구히 건너뛰어진다.
`fetch_titles(unresolved=...)` 가 둘을 갈라 준다.

### 문서가 없으면 Wikidata 한 줄이라도 (`--no-fallback` 로 끔)

`_labels` 는 라벨과 P31 만 물어본다. 그래서 엣지 반대편으로 딸려 들어온
노드는 이름만 있다. 위키백과 문서가 아예 없는 개체에는 Wikidata 의
`schema:description` 한 줄이 유일하게 남는 설명이다 — 한국어가 있으면
그대로 쓰고, 영어면 `koreanize` 로 옮겨서 넣는다.

영어도 받아 오는 이유가 있다. `Q117196164 황진` 의 한 줄은 `badminton
player` 다. 조선 인물이 아니라는 뜻이고, 비어 있을 때는 알 수 없던
사실이다. 다만 **영어 그대로 들어가지는 않는다** — '배드민턴 선수'로
옮겨서 넣고, 옮기지 못하면 넣지 않는다. 아래 "영어로 뜨는 설명" 참고.

### 화면에는 자료 출처를 적지 않는다

화면이 산문·한 줄·빈 칸을 다르게 그리되, **그 글이 어느 자료에서
왔는지는 말하지 않는다.** 출처 딱지는 읽는 사람이 묻지 않은 것을
답하면서 정작 궁금한 것(이 사람이 누구인가)을 밀어낸다. 수집 경로는
화면이 아니라 `props` 에 남는다.

| `props` | 화면 |
|---|---|
| `desc_source: kowiki` | 산문. 길면 `전문 보기` |
| `desc_source: wd:ko` / `사전` | 한 줄. 출처 표기 없음 |
| `desc_via: 의금부` | 산문 + `'의금부' 문서에서 넘겨받은 글입니다` |
| 빈 칸 | `설명 없음 — <왜 비었는지>` (소스별로 다른 문장) |

`desc_via` 는 출처 표기가 아니라 **'이 글이 이 노드의 글이 아닐 수
있다'는 경고**라서 남긴다.

`판의금부사` 의 설명은 `의금부` 문서의 글이다. 쓸모는 있지만 그 노드를
설명하는 글은 아니므로, 그렇다고 적어야 한다.

**넘겨주기와 정규화를 같이 세면 안 된다.** 응답의 문서명이 달라지는 이유는
둘인데, 넘겨주기는 *다른 문서*로 보내고 정규화는 표기만 손질한다
(밑줄·공백·유니코드 형태). 정규화까지 세면 같은 문서를 두고 "다른 문서에서
넘겨받았다"고 적게 된다 — 실제로 `김만기 (조선)` 한 건이 그랬다.
API 응답의 `redirects` 목록에 든 것만 `desc_via` 로 남긴다.

**넘겨받은 글은 추출에 넣지 않는다** (`load_documents`). 화면에서는 출처를
밝히고 보여주면 되지만, 추출은 다르다.

```
'무관랑'   ← '사다함' 문서
'이유'     ← '엠파이어 (음악 그룹)' 문서
```

이 글을 그 노드의 것으로 읽으면 **사다함의 관계가 무관랑에게 붙는다.**
근거 구절 검증도 이걸 못 막는다 — 인용한 구절은 원문에 실제로 있기
때문이다. 전체 그래프에 39건 있다.

### wd 가 아닌 노드는 이 경로로 채우지 않는다

조선 그래프에서 설명이 없는 나머지는 `extract` 970 · `timeline` 646 ·
`khs` 670 이다. 셋 다 위키백과 sitelink 가 없어서 `enrich` 가 닿지 못한다.

- `timeline` — `1443년` 같은 연표의 눈금이다. 채울 것이 없다.
- `extract` — 산문에서 이름만 뽑힌 노드다. 원문이 없다. 실제 노드로
  올리는 것은 `promote` 의 일이다.
- `khs` — 국가유산청이 `content` 를 빈 값으로 주는 유물이 9.3%(299건)
  있다. **API 응답을 직접 확인했다** — `통도사대웅전`·`강진 무위사
  극락보전` 모두 `<content/>` 가 비어 있다. 우리 파서의 문제가 아니라
  출처에 해설문이 없는 것이다.

**`same_as` 를 타고 설명을 빌려오지 않는다.** 설명 없는 khs 노드 670개
중 603개가 `same_as` 로 wd 노드에 이어져 있어 솔깃하지만, 상대가 같은
것을 가리키지 않는다.

```
khs:period '1360년(공민왕 9)판각'  same_as  wd:Q28179 조선
  → 빌려오면 '판각 연도' 노드가 조선 왕조의 설명을 달게 된다

kr:place:서울:종로구 '서울 종로구'  same_as  wd:Q8684 서울특별시
  → same_as 가 아니라 part_of 다. place_label_exact 92건 중 15건이
    이렇게 구·시를 상위 시·도에 붙여 놨다 (별도 결함)
```

빈 칸을 그대로 두고 왜 비었는지 적는 편이, 절반이 틀린 설명을 채우는
것보다 낫다.

## 핵심 사건 직접 수집 (`events`)

`enrich` 는 이제 남은 노드를 다 받지만, 그래도 **임진왜란·병자호란은
`enrich` 만으로 잡히지 않는다** — 그래프에 노드가 없으면 보강할 대상도
없고, 이 사건들은 Wikidata 상에서 연결이 적어 골격에 딸려 오지 않는다.
이름으로 직접 지정하는 경로가 따로 필요한 이유다.

분류 순회를 먼저 시도했으나 쓸 수 없었다. 한국어 위키백과의 사건 분류는
일관성이 없고(`분류:한국의_전쟁`, `분류:조선의_사건` 은 아예 없음), 실제
문서에 달린 분류는 `1636년 분쟁`, `깨진 링크를 가지고 있는 문서` 같은
연도·정비 분류가 대부분이다. 도메인 지식으로 직접 나열하는 편이 정확했다.

시드는 시대별로 묶여 있어 사건마다 `from_period` 엣지를 공짜로 얻는다.
문서명은 `extracts`+`pageprops` 한 요청으로 QID까지 함께 받아 `wd:Qxxxx`
노드로 만든다 — 기존 Wikidata 사건 노드와 자동으로 합쳐진다.

**본문 전체를 받는 것이 핵심이다.** 도입부만 받으면 사건 평균 380자인데,
"누가 무엇을 했는가"는 대부분 본문에 있다:

```
도입부만: 평균   380자 → 추출 대상 사건 33건
본문 전체: 평균 7,733자 → 추출 대상 사건 91건   (6·25 전쟁은 57,451자)
```

### 시드 표는 셋이다 — 단체와 개념은 사건이 아니다

시드 표 하나에 이름을 몰아넣으면 **들어오는 것이 전부 사건 노드가 된다.**
실측으로 `이봉창`·`윤봉길`이 사건 노드로 앉아 있었고(나중에 `reclassify`
가 인물로 옮겼다), 일제강점기를 넣으려니 의열단·조선총독부·창씨개명이
같은 함정 앞에 섰다. `upsert_nodes` 는 `type` 을 덮어쓰지 않으므로 이미
앉은 노드는 안전하지만, **처음 들어오는 이름은 시드 표가 타입을 정한다.**

그래서 표를 셋으로 갈랐다 — `EVENT_SEEDS`·`ORG_SEEDS`·`CONCEPT_SEEDS`.
`events --kinds org` 처럼 골라 돌릴 수 있고, 표가 말한 타입과 그래프에
앉은 타입이 다르면 조용히 넘어가지 않고 반드시 한 줄로 보고한다.

가르는 기준은 "언제 시작하고 끝났는지 하나로 적을 수 있는가"다.
조선 토지 조사 사업(1910~1918)은 사건이고, 무단 통치는 개념이다.

### 일제강점기 — 없던 것은 인물이 아니라 사건이었다

일제강점기 35년의 사건 노드가 **13개**였다. 원인은 셋이었고 전부 수집
쪽이었다 (2026-09-04 실측):

| 무엇이 없었나 | 고친 뒤 |
|---|---|
| 사건 시드 11개 (그중 2개는 사람) | 사건 33 · 단체 28 · 개념 8 |
| `POLITIES` 에 일제강점기가 없음 → P27 인물 2,082명을 한 번도 안 물어봄 | 인물 1,339명 수집 |
| 시드로 들어온 사건에 연대 없음 → 연표에 설 자리가 없음 | 연대 있는 1905~1945 사건 22 → 58개 |

`Q503585`(일제강점기)는 왕조가 아니라 기간이라 `period` 노드로 세운다.
통치 주체인 일본 제국을 시대 이름으로 쓸 수 없어서다 — "일제강점기의
사건"과 "일본 제국의 사건"은 다른 말이다.

**시대가 장소로 앉아 있었다.** `wd:Q503585` 는 원래 `place` 노드였고,
인물 44명의 출생지와 2명의 사망지가 거기로 가 있었다 — 화면은 "나운규는
일제강점기에서 죽었다"고 말한다. Wikidata 의 P19 가 '일제강점기 조선'을
답으로 주는데 그대로 장소로 받아 적은 탓이다. 같은 모양으로 **고려도
장소였다.** 지우지 않고 `from_period` 로 옮긴다 — '언제'를 '어디서' 칸에
적은 것뿐이라, 옮기면 그 시대 사람이라는 원래 맞는 사실로 남는다
(`resolve.fix_period_nodes`, 94건).

### 인물은 국적이 아니라 연대로 고른다

`scope` 는 인물 씨앗을 국적(P27)으로 골라 왔다. 조선까지는 통했지만
일제강점기에서 무너진다 — **나라가 없던 시대라 같은 시대 사람이 국적표
여섯 칸에 흩어져 있다:**

| 인물 | 태그된 국적 |
|---|---|
| 유관순 · 신채호 · 이봉창 · 이육사 | 일제강점기 |
| 이완용 · 홍범도 · 한용운 · 이광수 | 조선 |
| 김좌진 · 여운형 · 손병희 · 방정환 | (없음) |
| 박은식 · 지청천 | 대한민국 |
| 안중근 · 조만식 | 대한제국 |
| 김원봉 | 조선민주주의인민공화국 |

게다가 P27 이 '일제강점기'로 적힌 1,339명은 **81%가 1960년 이후에 죽었다** —
그 시대에 태어났을 뿐인 해방 후 인물 명단이다. 그대로 씨앗으로 삼으면
1960년대 국회의원과 배우가 독립운동가보다 많은 그래프가 된다.

갈리는 것은 연대다. `Era.person_window` 가 그 규칙이다 — 생년 ≤ 시대
시작연도이고 몰년 ≥ 시대 시작연도(몰년을 모르면 한 생애 안). 실측
2,187명이 걸리고 위 표의 21명이 **전원** 들어온다.

### 훈장이 사건이었다 — 계층 추론보다 손으로 확인한 표가 앞선다

연대를 채우자 연표가 이렇게 말했다: "1900년에 일어난 일 — 대훈위
금척대수장, 태극장, 자응장, 팔괘장". 훈장 노드가 사건으로 앉아 있었고,
`reclassify` 도 그것을 사건으로 판정했다. Wikidata 의 사건 계층이 허술해서
**`state order`(훈장)도 `shipyard`(조선소)도 `Q1190554 사건`에 닿기**
때문이다 (대한조선공사가 사건이었다).

`reclassify` 의 사다리에 관문을 하나 더했다: **P31 이 하나도 빠짐없이
`WD_CLASS_TO_TYPE` 에 있고 한 타입으로 모이면, 계층을 걷기 전에 그 표를
믿는다.** 표는 라벨을 대조해 손으로 적은 것이고 계층은 추론이다. 표
**전체**를 앞세우면 반대로 다치므로(제2차 세계 대전의 P31 에 '시대'가
섞여 있다) 조건이 둘이다 — 전부 표 안에 있을 것, 한 타입으로 모일 것.
17개가 옮겨졌고(훈장 16 · 조선소 1), 어긋난 엣지는 519건에서 13건이 됐다.

### 긴 문서는 조각낸다

본문 전체를 통째로 한 요청에 넣으면 뒤쪽 문단의 관계를 놓친다. 6,000자
단위로 **문단 경계에서** 자르고 400자씩 겹친다. 문단 중간에서 자르면
`이순신은 …` / `… 명량에서 승리했다` 처럼 주어와 서술이 갈라져 관계가
통째로 사라진다.

## 산문에서 관계 추출 (`extract`)

인물↔사건 엣지의 유일한 현실적 공급원. Claude API(`claude-opus-5`)로
산문에서 관계를 뽑는다.

- **가제티어 그라운딩** — 그래프에 이미 있는 개체명을 프롬프트에 넣어
  모델이 같은 표기를 쓰게 한다. 이게 없으면 추출 결과가 기존 노드에
  붙지 않는 고아가 되어 그래프가 연결되지 않는다.
- **이름이 여럿을 가리키면 잘 연결된 쪽** — 라벨과 별칭을 함께 놓고
  차수로 고른다. 실측: 태조의 아들 관계가 관계 24건짜리 조선 정종이
  아니라 엣지 1개짜리 동명 노드에 붙어, 화면에서 정종이 아버지도 형제도
  없는 외톨이가 됐다. 우리 라벨은 '조선 정종'인데 산문은 '정종'이라
  쓰기 때문에 생긴 일이라, `promote` 가 왕조 접두를 뗀 별칭을 달아준다.

### 족보 목록은 모델을 망가뜨린다 — 지우고 넣는다

인물 문서의 '가족 관계' 절은 서사가 아니라 목록이다.

```
증손부 : 창녕조씨(昌寧曺氏) - 조이태(曺爾泰)의 따님.
손서 : 박세형(朴世亨) - 본관은 진원(珍原)
장남 : 안후지(安厚之, 1590~1664)
```

안방준 문서는 조각 1의 74%, 조각 2의 90%가 이런 행이었다. 그대로 넣으면
세 가지가 한꺼번에 무너진다.

1. **방계가 본인의 배우자가 된다.** 증손자의 아내 창녕조씨가
   `안방준 --spouse_of--> 창녕조씨` 로 나온다. 필드의 주인이 문서 주인이
   아닌데 모델은 그렇게 읽는다.
2. **방향이 뒤집힌다.** `장남 : 안후지` 에서 `안방준 --child_of--> 안후지`.
3. **모델이 루프를 돈다.** 같은 관계 블록을 네 번 반복해서 뱉는다.
   조각당 350초가 그렇게 쓰였다.

**근거 검증이 이걸 못 잡는다** — 근거 구절이 원문에 실제로 있기 때문이다.
그래서 `strip_kinship_lists` 가 **선별 이전에** 목록 행을 지운다. 선별
이후에 지우면 이미 늦다: 이름이 빽빽한 족보 조각이 밀도 점수를 부풀려
서사 조각을 밀어내고 상위 3조각을 차지한다.

직계 가족을 잃지는 않는다. `아버지는 첨지중추부사 안중관이며, 처는 경주
정씨 판관 정승복의 딸이다` 같은 **서사 문장은 그대로 남고**, 거기서 올바른
방향으로 뽑힌다.

### 소유격을 삼키면 한 세대가 사라진다

```
처는 경주 정씨 판관 정승복(鄭承復)의 딸이다.
        → 안방준 --spouse_of--> 정승복      ✗
```

안방준의 아내는 정승복의 **딸**이지 정승복이 아니다. 근거 검증은 이걸
못 잡는다 — 근거 구절이 원문에 그대로 있기 때문이다. 한국어 인물 산문에서
여성이 이름 대신 `누구의 딸` 로만 적히는 일이 흔해 이 형태가 반복된다.
딸의 이름이 원문에 없으므로 고쳐 붙일 수 없고, 버리는 것이 맞다.

**함정은 관계 타입마다 판정이 뒤집힌다는 것이다.** `A --child_of--> B` 는
'A 는 B 의 자녀'라는 뜻이므로

```
안중관의 아들 안방준은 …
        → 안방준 --child_of--> 안중관       ✓ 옳다
```

같은 소유격이 `spouse_of` 에서는 오류고 `child_of` 에서는 정답이다. 한
규칙으로 뭉뚱그리면 맞는 부모 관계를 버린다. `child_of` 에서 버려야 할
것은 `X의 손자` 처럼 **두 세대 이상** 건너뛴 경우뿐이다.

### 가족 관계는 인포박스가 더 정확하다 (`infobox --types person`)

같은 정보를 LLM 없이 얻는 길이 있다. 인포박스는 필드의 주인이 명확하다.

```
|아버지 = [[안중관]]      → 주인이 출발점
|자녀   = [[안후지]]      → 주인이 도착점 (방향이 반대다)
```

같은 `child_of` 인데 필드에 따라 방향이 갈리므로 필드마다 방향을 적어
둔다(`PERSON_FIELDS` 의 `OUT`/`IN`). 테스트가 이 표를 온톨로지의
`EDGE_TYPES` 와 대조한다 — 어긋나면 엣지가 통째로 버려지기 때문이다.

두 관문이 쓰레기를 막는다. 실측:

| 링크 | Wikidata 판정 | 결과 |
|---|---|---|
| `첩` | role | 제외 (사람이 아니다) |
| `이정 (1511년)` | person | `이순신 --child_of--> 이정` |
| `조선민주주의인민공화국` | place | **최협의 규칙으로 제외** |

마지막 줄이 타입 관문만으로는 부족한 이유다. 위키백과 지명 필드는
`[[고려]] [[개성특급시]] [[선죽교]] [[조선민주주의인민공화국]]` 처럼 넓은
곳부터 쌓이고 현대 행정구역이 섞인다. 국가는 Wikidata 에서 `place` 로
오므로 타입 검사를 통과해 `정몽주 --died_in--> 조선민주주의인민공화국`
이 만들어진다. 1392년에 죽은 사람에게 1948년 국가를 붙이는 셈이다.
출생지·사망지는 **가장 구체적인 링크 하나만** 쓴다.

### 이름이 엉뚱한 노드에 붙었는지 전수 조사 (`promote`)

이름으로 노드를 찾는 것은 추출뿐이다 — 나머지 소스는 QID·유물번호가
키라서 엉뚱한 데 붙을 수가 없다. 그래서 추출 엣지의 끝점을 전부 훑는다.

```
끝점 1,944개 검사 → 이상 없음 1,898 · 옮김 21 · 보류 8
```

셋으로 갈린다.

| 판정 | 근거 | 예 |
|---|---|---|
| 이상 없음 | 이미 후보 중 가장 잘 연결된 노드에 붙어 있다 | 김규식(8) ↔ 동명 3명(1,2,1) |
| 옮김 | 문서의 시대와 후보의 시대가 맞는다 | 갑자사화 문서의 '태조' → 조선 태조 |
| 옮김 | 차수가 압도적이다 (5배 이상, 본인 ≤2) | '1920년' → `time:1920` |
| 보류 | 진짜 동명이인이라 규칙으로 못 가른다 | 김구(6) ↔ 김구(7) ↔ 김구(5) |

**시대는 문서가 알려준다.** 추출 엣지는 어느 글에서 나왔는지를
`props.extracted_from` 에 남긴다. 갑자사화 문서에서 나온 '태조'는 조선
태조지 고려 태조가 아니다 — 전체 그래프만 보면 절대 알 수 없고, 이 한
줄이 있어야 판정이 선다.

**보류는 그대로 둔다.** 김구가 셋이면 그건 데이터가 틀린 게 아니라 실제로
사람이 셋인 것이다. 차수가 엇비슷한 후보를 자동으로 고르면 절반은 틀린다.

노드를 합치지 않고 **엣지만** 옮긴다. 동명 노드도 실재하는 인물이라
지우면 안 된다 — 그 문장이 말한 사람이 아니었을 뿐이다.
- **structured outputs** — `output_config.format` 의 JSON 스키마로 응답
  형태를 강제한다. 파싱 재시도 루프가 필요 없다.
- **Batch API 기본값** — 추출은 실시간성이 필요 없으므로 표준 요금의
  50%인 배치로 처리한다. `--sync` 는 소량 테스트용.
- **근거 보존** — 모든 추출 엣지는 원문 구절을 `props.evidence` 에 남긴다.
  출처 없는 추론은 나중에 검증할 수 없다.
- **거절 처리** — Claude Opus 5 는 안전 분류기가 요청을 거절할 수 있다
  (HTTP 200 + `stop_reason: "refusal"`). `content` 를 무조건 인덱싱하면
  거기서 깨지므로 먼저 `stop_reason` 을 확인한다.

비용을 쓰기 전에 `extract --dry-run` 으로 실제 프롬프트를 확인할 것.

## 추출 고아를 실제 노드로 (`promote`)

추출은 그래프에 없는 이름을 만나면 `ex:{타입}:{이름}` 노드를 만든다.
그게 598개까지 쌓였고, 두 가지가 섞여 있었다.

| 원인 | 예 |
|---|---|
| 표기가 어긋남 | 우리 라벨은 `조선 세조`, 산문은 `세조` |
| 애초에 그래프에 없음 | 신규식·이종일·길선주 (Wikidata 국적 태그 누락) |

**두 번째가 대부분이다.** ex 인물 라벨 597개 중 전체 그래프에 같은
라벨이 있는 것은 **0개**였다 — 표기 문제가 아니라 진짜 신규 인물이다.

값싼 순서로 세 단계를 거친다. 뒤 단계는 앞이 못 붙인 것만 처리한다.

```
retype  타입 오분류 교정            74건  ('조선총독부'가 person 이었다)
local   라벨·왕조접두·별칭 매칭      28건  (네트워크 불필요)
kowiki  문서명 → QID → wd: 승격     87건
```

승격은 **병합**이다. ex 노드를 지우고 엣지를 대상 노드로 옮긴다. 옮기지
않고 `same_as` 만 걸면 화면에는 같은 인물이 여전히 둘로 보인다. 되돌릴
수 있도록 원래 표기는 별칭으로 남기고, 대상 노드 props 에 `merged_from`
(무엇을·어떤 근거로 합쳤는지)을 쌓는다.

### 자료는 순서대로 오지 않는다 (`alias_exact`)

화면의 **정여립의 난에 정여립이 없었다.** 설명도 없고 관계가 하나뿐인
빈 노드가 떴다. 그런데 정여립은 그래프에 멀쩡히 있었고, 사건도 있었다 —
`기축옥사`라는 **다른 이름으로** 옆에 따로 서 있었다.

```
ex:event:정여립의 난   관계 1   이산해 ← related_to        설명 없음
wd:Q7836645 기축옥사   관계 3   정여립 ← participated_in   설명 있음
                              별칭: 기축사화 · 정여립의 난 · 정여립의 옥사
```

**추출은 이름을 찾을 때 별칭을 본다.** 그런데 그건 *추출이 돌던 그
순간의* 별칭표다. 날짜를 보면 원인이 다 나온다.

| 시각 (KST) | 일어난 일 |
|---|---|
| 08-31 05:25 | 이산해 문서 추출 → `정여립의 난` 을 못 찾아 `ex:` 노드를 만듦 |
| 09-03 12:47 | `aliases` 명령을 처음 만들어 돌림 → 그 이름이 기축옥사의 별칭이 됨 |
| — | **아무도 다시 해소하지 않았다** |

`fetch_aliases` 는 8월 13일부터 있었지만 파이프라인에서 부르는 곳이 없는
죽은 코드였다. 사흘 차이로 화면이 틀렸다.

**해소는 한 번 일어나고 끝났다.** 뒤늦게 온 별칭·노드는 이미 만들어진
고아를 되돌리지 않는다. 그래서 `local_matches` 가 별칭도 라벨과 같은
무게로 보게 했다 — `promote` 가 곧 **오늘의 별칭표로 다시 해소하는**
단계다.

사건에는 이 길밖에 없었다. `kowiki_matches` 는 사건에 대해 넘겨주기를
일부러 안 따라가는데(바로 아래 참조) 정여립의 난은 위키백과에서 기축옥사로
넘겨주기다. **두 문이 다 닫혀 있었다.**

거는 조건은 점수가 아니라 규칙이다.

- **그 이름으로 불리는 같은 타입 노드가 딱 하나일 때만.** 별칭은 라벨보다
  붐빈다 — `add_bare_name_aliases` 가 '조선 정종'·'고려 정종' 양쪽에
  '정종'을 달아두므로 왕의 휘는 후보 둘이 되어 저절로 걸러진다.
- **라벨 일치가 앞선다.** 라벨이 정확히 같은 후보가 있으면 별칭 단계까지
  오지 않는다 (하나면 이미 이었고, 둘이면 이미 포기했다). 별칭이 남의
  라벨을 밀어내는 일은 없다.
- **연대가 어긋나면 안 잇는다.** `kowiki_matches` 가 승격 전에 하는
  검사를 여기서도 한다.

실측 18건(전체 12 · 조선 6), 손으로 다 확인했고 오탐 0.

```
정여립의 난 → 기축옥사        갑오경장 → 갑오개혁       한일 합방 → 한일병합
진산사건 → 신해박해           남원성 전투 → 남원 전투    경덕궁 → 경희궁
제1차 진주성 전투 → 진주대첩   광주학생운동 → 광주 학생 항일 운동
남북협상 → 전조선 제정당사회단체 대표자 연석회의        황주·화순 → 황주군·화순군
```

병합 뒤 `정여립의 난`으로 검색하면 별칭을 타고 기축옥사가 나오고, 그
안에 정여립이 있다.

### 이름만 같은 사람을 걸러내는 네 관문

문서명으로 QID 를 찾는 건 쉽다. **틀린 QID 를 안 붙이는 게 어렵다.**

| 관문 | 실측 |
|---|---|
| 동음이의 문서 제외 | 49건 — `선조` 는 목록 문서다 |
| Wikidata 클래스(P31/P279*) 대조 | 26건 — 타입이 다르면 잇지 않는다 |
| 연대 대조 | 2건 — 아래 참조 |
| 사건은 넘겨주기 미추적 | `곽산 학살 사건` → `3·1 운동` |

연대 대조가 실제로 잡은 것:

> 무오사화 문서에 나온 `한유` 를 문서명만 보고 승격하면 당나라 문인
> 韓愈(768~824)에 붙는다. 이웃 노드인 김종직(1431~1491)과 600년이
> 어긋난다.

이웃 노드(추출 출처 문서 포함)의 연대와 후보의 생몰년이 150년 넘게
어긋나면 동명이인으로 보고 건너뛴다. **근거가 없으면 막지 않는다** —
모르는 것을 틀렸다고 판정하면 멀쩡한 승격이 사라진다.

사건에만 넘겨주기를 끄는 이유는 방향이 다르기 때문이다. 인물의
넘겨주기는 이름 이표기(`리델` → `펠릭스클레르 리델`)지만, 사건의
넘겨주기는 하위 항목이 상위 항목을 가리킨다. 따라가면 개별 사건이 큰
사건에 흡수돼 해상도가 사라진다.

### 승격의 값은 관계 보강에서 나온다

QID 를 찾아 노드를 만드는 것까지는 이름을 바꾼 데 지나지 않는다. 그
QID 에 달린 관계를 끌어와야 고아였던 인물이 그래프에 얽힌다.

```
승격 노드 69개 → 관계 189건 · 상대 노드 178개
유관순: participated_in 천안 아우내 만세운동 (추출)
      + born_in 천안시 · died_in 서대문형무소 · participated_in 3·1 운동 (Wikidata)
```

기존 `fetch_person_edges` 로는 이들이 영원히 안 들어온다 — 국적(P27)으로
대상을 고르는데, 승격된 인물은 **바로 그 태그가 없어서** 빠진 사람들이다.
QID 를 직접 지정하는 `fetch_edges_for` 가 따로 필요했다.

### 타입 교정은 접미사 규칙이지만 오탐이 더 위험하다

`~총독부`·`N인`·`~일파`·`~판서`·`~감사` 같은 규칙은 잘 듣는다. 다만
규칙을 라벨 **끝**이나 **전체**에만 건다 — 가운데를 보면
`간도 일본 영사관 습격`(사건)이 영사관 때문에 조직이 된다. `정부` 는
접미사로 쓰지 않고 관청 이름을 나열한다. 그래프에 `김정부` 라는 인물이
실제로 있다.

## 화면 (`serve`)

```bash
uv run histgraph serve          # http://127.0.0.1:8100  (data/korea.sqlite)
```

서버는 여전히 표준 라이브러리뿐이다. 화면은 React + d3-force 를 쓴다 —
`/api/*` 는 JSON, 나머지는 정적 파일이라는 갈래는 그대로다.

**화면은 이제 빌드해야 한다.** JSX 는 브라우저가 직접 못 읽는다. `npm run
build` 가 만든 `web/dist/` 를 `serve` 가 내주고, 그게 없으면 무엇을 하라고
적어 준다 (`server.warn_if_unbuilt`). 고치는 중이라면 빌드 대신 `npm run
dev` 를 쓴다.

### 화면만 따로 고칠 때 (`npm run dev`)

화면을 고치는 동안에는 빌드를 다시 돌리는 대신 HMR 을 쓴다. API 는 파이썬이
그대로 맡고, Vite 가 `/api` 를 8100 으로 넘긴다.

```bash
npm install               # 처음 한 번
npm run dev               # API(8100) + 화면(5173) 을 함께
```

→ **http://127.0.0.1:5173**

브라우저는 **5173 하나만** 본다 (`/api` 는 8100 으로 프록시된다 —
`web/vite.config.js`). Ctrl+C 로 둘 다 접힌다.

Vite 기본값(`localhost`)은 맥에서 IPv6 `[::1]` 에만 붙어, 8100 습관대로
`127.0.0.1:5173` 을 치면 연결이 거부됐다. 설정에 `host: '127.0.0.1'` 을 박아
API 와 같은 스택에 세웠다 — 두 포트를 같은 주소로 친다.

`serve` 에 줄 인자는 그대로 넘어간다:

```bash
npm run dev -- --db data/histgraph.sqlite    # 전체 그래프로
```

한쪽만 따로 띄우려면 `npm run dev:api` (8100) · `npm run dev:web` (5173).

배선은 `tools/dev.sh` 다. 두 가지를 지킨다 — **8100 이 이미 떠 있으면 그대로
쓴다** (남의 터미널 것을 뺏지도, 끄면서 죽이지도 않는다). 그리고 **이 셸이
끝나면 자기가 띄운 API 도 접는다** — 5173 을 닫았는데 8100 이 남아 다음
실행을 막는 걸 본다.

저장소 루트에서 친다. 프론트 설정의 본체는 `web/package.json` 이고 루트의
것은 `--prefix web` 으로 넘기기만 한다 — 화면 파일이 `web/` 에 모여 있는
것과, 루트에서 `npm run dev` 가 그냥 되는 것 둘 다 지키려는 것이다.

`npm run build` 가 만든 `web/dist/` 를 `serve` 가 내준다 (`server._web_root`).
8100 에서 옛날 화면이 보인다면 `dist/` 가 낡은 것이다 — 다시 빌드한다.

### 화면 구조 (React)

React 는 **껍데기만** 맡는다 — 머리·검색·사이드·상세 패널. 캔버스는 초당
60번 다시 그려지는 곳이라 가상 DOM 을 통과시킬 이유가 없어서, `GraphView`
와 `TimelineRail` 은 React 를 모르는 명령형 클래스로 남았다. React 쪽은
`useRef` 로 자리를 잡아주고 **수명만** 관리한다 (`destroy()` 를 부르지
않으면 RAF 루프와 ResizeObserver 가 죽은 캔버스를 붙잡고 계속 돈다).

콜백은 ref 에 담아 넘긴다. 그냥 넘기면 `onSelect` 가 바뀔 때마다 `GraphView`
를 새로 만들어야 하고, 그러면 펼칠 때마다 배치가 처음부터 다시 튄다.

**배치는 d3-force 로 옮겼다.** 손으로 짠 1/d² 반발력은 근거리에서 강성이
폭발해 진동했고, 그걸 최소거리로 잘라 막고 있었다 — d3 는 같은 문제를
`forceCollide` 로 푼다. 다만 **틱은 여전히 직접 돌린다**: 힘 계수가 전부
"한 틱당"으로 잡혀 있어서 d3 타이머에 맡기면 120Hz 화면(ProMotion)에서
힘이 두 배로 들어간다.

색은 손대지 않았다. `uv run tools/check_palette.py` 가 그대로 통과한다
(정상 10.7 · 2형 5.9 · 1형 5.7).

|---|---|
| `layout.test.mjs` | 배치가 식는가 · 겹치지 않는가 · 중심이 가운데를 지키는가 |
| `relations.test.mjs` | 조사·문장·카드 합치기 (실측 버그들이 쌓인 자리) |
| `render.test.mjs` | 서버 렌더링으로 실제 조립 · **화면에 영어가 새지 않는가** |

`render.test.mjs` 는 esbuild 로 컴포넌트를 묶어 `renderToString` 을 돌린다.
컴포넌트를 함수로 직접 부르면 훅이 React 바깥에서 돌아 터지므로 반드시
`createElement` 로 감싼다.

### 중심은 왕조다

화면을 열면 **조선**에서 시작한다 (노드 106 · 관계 118 — 왕후·공신 64명과
사화·전란·개혁 41건이 왕조를 둘러싼다). 차수 1위 노드로 열지 않는다.
그건 그때그때 병자호란이었다가 선조였다가 하는 우연이고, "이게 무엇의
그래프인가"를 말해주지 못한다.

시대를 바꾸면 중심도 따라 바뀐다 — `scope.ERAS` 의 왕조 QID 를 쓰므로
고려 그래프의 중심은 고려다. 그 노드가 실제로 없으면 중심을 지어내지 않고
차수 상위 시작점만 보여준다.

### 시대 묶음 (`scope korea`) — 1910년에서 끊지 않는다

화면이 읽는 것은 `data/korea.sqlite` 다. **시대 하나가 아니라 묶음이다**
(`scope.BUNDLES`): 조선·일제강점기·대한민국을 한 DB 에 담아 1392년부터
지금까지가 연표에서 끊기지 않는다. 조선을 1910년에서 자르면 그 다음 35년이
화면 어디에도 없고, 사람도 이어진다 — 대한제국에서 벼슬한 사람이
일제강점기에 의병이 되고, 조선의 마지막 왕이 일제강점기의 이왕(李王)이다.

**대한민국은 씨앗을 다르게 고른다** (2026-09-04). 다른 시대는 국적(P27)
으로 인물 씨앗을 고르는데, 대한민국 국적은 전체 인물의 65%(18,471명)이고
그 대부분은 운동선수·연예인이다 — 국적으로 고르면 역사가 아니라 명단이
된다. 그래서 `Era.seed_by_polity=False` 로 국적을 끄고, 씨앗은 **사건**
(시드 표 + P17 태그)과 **대통령 자리에 앉았던 사람**(`Era.seed_positions`)
에서만 온다. 사람은 그 이웃으로 들어온다. 정체 노드(Q884)는 출생지 엣지
983건이 가리키는 **장소**라 시대 엣지의 도착이 못 되고, 그래서 이 시대는
`from_period` 가 없다 — 씨앗은 props 의 태그로 고른다. P17 은 '지금 그
땅의 나라'를 적기도 해서(원종·애노의 난 889년이 대한민국 사건으로 태그돼
있다) `Era.since` 앞의 사건은 태그가 있어도 뺀다.

씨앗은 **시대별로 따로** 고르고(기준이 시대마다 다르다) 확장·고립정리·
복사는 합집합에 한 번만 한다. 시대별로 뽑아 나중에 합치면 시대를 걸치는
엣지가 양쪽 어디에도 안 남는다.

머리말에 뜨는 이름(`조선~대한민국`)은 **서버가 준다**(`meta.era_label`).
화면이 영어 키를 한국어로 옮기는 표를 따로 들고 있으면 시대를 더할 때마다
두 곳을 고쳐야 하고, 빠뜨린 하나가 그대로 영어로 뜬다.

```
                조선만      조선~일제강점기    조선~대한민국
노드             7,133          9,717           10,444
엣지            13,601         20,267           23,484
사건               407            519              630
단체               126            185              192
```

### 이웃끼리의 관계도 함께 준다 (유도 부분그래프)

탐색하면서 모은 엣지는 **프론티어에 닿는 것뿐**이다. 그것만 돌려주면
중심에서 바큇살만 뻗은 그림이 되고, "인조반정과 병자호란이 이어져 있다"
같은 것이 화면에서 통째로 사라진다. 노드 집합이 정해진 뒤 **그 안의 모든
엣지**를 다시 물어봐야 한다.

```
조선 주변 (1단계)   중심에 닿는 118 + 이웃끼리 23   ← 23건이 빠져 있었다
조선 주변 (2단계)   중심에 닿는 118 + 이웃끼리  64
```

기본값이 2단계인 이유가 여기 있다. 왕조의 직접 이웃은 원래 서로 잘 안
닿는다 — 인물과 사건이 얽히는 것은 한 홉 더 나가서다. 이순신을 열면
94개 노드에 명량 해전·임진왜란과 그 참전자들이 함께 온다.

### 전부 그리지 않는다

조선 그래프는 노드 5,637 · 엣지 9,629 다. 한 화면에 다 뿌리면 브라우저는
그리지만 사람은 못 읽는다. 그래서 서버는 **언제나 한 노드 주변만** 돌려주고,
왕조에서 시작해 이웃을 펼쳐 나가는 방식으로 읽는다.

상한(기본 120개)에 걸리면 **차수 높은 이웃부터** 남긴다. id 순으로 자르면
`wd:Q1…` 이 먼저 살아남을 뿐이라 무엇이 남는지가 우연에 맡겨진다.

연도(`period`) 노드는 기본으로 뺀다. 거의 모든 노드에 붙어 있어서 그냥 두면
화면 예산을 연도가 다 먹고 정작 인물·사건이 밀려난다. 체크박스로 켤 수 있다.

### 색이 타입을 말한다 (모양은 걷어냈다)

노드 타입은 9종이다. 한때는 색을 큰 갈래 4개로만 쓰고 세부 타입은 **모양**
으로 갈랐다 — 인물은 원, 단체는 육각형, 사건은 마름모, 장소는 사각형…
지금은 모양을 하나(원)로 두고 색 아홉이 타입을 말한다.

갈래는 **색상 계열**로 남는다. 인물·단체는 파랑~보라, 사건은 주황,
장소·유물·작품은 초록~금~분홍~청록, 시대·직위는 무채색. 그래서 색이
아홉이어도 화면은 먼저 네 덩어리로 읽히고 그 안에서 타입이 갈린다. 뼈대
(시대·직위)는 어둡게 묶어 물러나 있게 했다.

**색 거리는 재서 안다.** `uv run tools/check_palette.py` 가 `web/src/lib/graph-view.js`
에서 팔레트를 직접 읽어 잰다 (OKLab ΔE ×100, 색약은 Viénot 1999). 처음 고른
아홉 색은 눈금(5.0) 아래였고, 색상만으로 벌린 탓이었다. **밝기까지 층으로
갈라** 다시 골랐다 — 색을 잃은 눈에 남는 것은 밝기다:

| 잰 것 | 정상 시야 | 2형(deutan) | 1형(protan) |
|---|---|---|---|
| 옛 팔레트 · 타입 9색 — 색상만으로 벌림 | 4.3 | 2.6 | 2.0 |
| 옛 팔레트 · 갈래 4색 (모양이 타입을 나르던 때) | 12.4 | 2.6 | 5.2 |
| **지금 팔레트 · 타입 9색 — 밝기까지 벌림** | **10.7** | **5.9** | **5.7** |
| 지금 팔레트 · 갈래 4색 (타입을 모를 때 물러날 자리) | 19.2 | 6.4 | 10.5 |

**앞의 두 줄은 옛 팔레트를 잰 기록이다.** 지금 `check_palette.py` 를 돌리면
아래 두 줄이 찍힌다 — 검증기는 `graph-view.js` 를 읽으므로 늘 지금 색을
잰다. 옛 값과 나란히 두는 것은 무엇이 나아졌는지 견주려는 것이지, 같은
것을 두 번 잰 것이 아니다.

**눈여겨볼 것은 옛 갈래 4색의 2형 값이 이미 2.6 이었다는 점이다.** 색을
넷으로 줄여도 색약에서는 갈래끼리 구별되지 않았다. 그때 타입을 나르던 것은
색이 아니라 **모양**이었다. 모양을 걷어낸 지금은 색이 그 짐을 다 지므로,
아홉 색이 그때의 갈래 넷보다 오히려 잘 갈린다 (2형 5.9 대 2.6).

그래도 5.9 는 "다르다"이지 "나란히 놓지 않아도 읽힌다"가 아니다. 노드는
화면에 흩어져 있고 작다. 그래서 **색으로만 뜻을 나르는 자리를 만들지
않는다.** 범례는 색 견본 옆에 타입 이름을 적고(갈래 머리는 견본 없이 글자만),
노드를 고르면 상세 패널이 타입을 글자로 말한다. 캔버스만 보고 타입을 알아야
하는 상황을 남기지 않는 것이 지금 설계가 기대고 있는 전제다.

3형(tritan)은 도구가 함께 찍지만 판정에는 쓰지 않는다. Viénot 의 방법은
저자가 1·2형에만 유효하다고 밝힌 것이라, 3형은 방식에 따라 같은 팔레트가
6 과 14 로 갈린다.

옛 표(8색 1.6 · 4색 1.9 · 3색 9.4)를 만든 검증기는 저장소에 없었고 시뮬레이션
방식도 남아 있지 않아 위 수치와 곧바로 견줄 수 없다. `tools/check_palette.py`
는 방식을 코드에 적어 두었으니 다시 잴 때마다 같은 값이 나온다.

선도 마찬가지다. 실선은 구조화 소스, **점선은 산문에서 추출한 관계**,
가는 점선은 `same_as`. 어디서 온 사실인지 화면에서 구분되지 않으면 둘 다
못 믿게 된다.

이름표는 **자리가 있으면 붙이고 없으면 만다**. 겹치는지를 실제로 재서
정한다 — '차수 6 이상만' 같은 기준은 화면 사정과 무관해서, 왕조를 중심에
놓으면 왕후 수십 명이 이름 없는 파란 점이 된다. 확대하면 자리가 생기면서
더 많은 이름이 저절로 드러난다.

### 배치가 화면 밖으로 달아나지 않게

힘기반 배치는 초반에 폭발하기 쉽다. 세 가지로 묶어둔다.

- **시작 위치를 황금각 나선에 고르게 놓는다.** 무작위로 뿌리면 몇 개가
  거의 겹친 채 시작하고, 그 지점의 반발력이 폭발해 서로를 화면 밖으로
  튕겨낸다.
- **한 틱에 움직일 거리를 묶는다.** 한번 수천 px 밖으로 나간 노드는
  돌아오는 속도가 `alpha` 에 비례해 줄어들어 영영 못 돌아오고, 그
  한두 개 때문에 나머지 전부가 좁쌀만 하게 축소된다.
- **식을 때까지 카메라가 따라간다.** 한 번만 맞추면 그 뒤로도 배치가
  퍼져서 결국 화면이 빈다 (실측: 6초에 화면의 16%를 채우던 그래프가
  20초에 1%만 남았다). 사용자가 화면을 움직이기 시작하면 손을 뗀다.

### 근거를 띄운다

노드를 고르면 관계가 종류별로 묶여 나오고, 각 관계에 **출처와 근거 구절**이
붙는다.

```
참여 · 5
  명량 해전        추출 0.9
    “1592년 7월 8일 이순신이 한산도 대첩에서 일본 수군 주력 부대를 격파해…”
  노량 해전        인포박스 0.9
```

신뢰도 숫자만 보여주면 0.9가 LLM 추출인지 인포박스 파싱인지 알 수 없다.
판단은 출처를 알아야 할 수 있다.

**같은 사실을 두 소스가 말하면 한 줄로 합쳐 보여준다.**

```
행주산성    Wikidata + 인포박스     ← 두 소스가 확인했다
경기도      인포박스 0.9
```

저장소에는 소스별로 그대로 둔다 — `(출발, 도착, 관계, 출처)` 가 자연키라
교차검증의 근거가 된다. 하지만 화면에 '행주산성'이 두 번 나올 이유는
없다. 실측: 전체 57,493개 사실 중 81건을 두 소스 이상이 말한다. 신뢰도는
가장 높은 소스 것을 쓰고(Wikidata 1.0 이 인포박스 0.95 를 이긴다),
확인해 준 소스는 모두 적는다.

`store.neighbors` 는 **자연키(출처 포함)로** 중복을 없앤다. 출처를 뺀
키로 합치면 둘 중 하나가 조용히 사라져, 화면이 어느 소스가 확인해 줬는지
알 수 없게 된다. 한 줄로 합칠지는 화면이 정할 일이다.

### 연표 — 몇 년쯤인가, 무엇 뒤 무엇 앞인가

그래프는 무엇이 무엇과 이어져 있는지만 말하고 **언제인지는 말하지 않는다.**
그래서 노드를 고르면 왼쪽에 세로 연표가 함께 선다.

```
연표
1504년  [연결된 연도]
1356 ▭▭▭▮▭▭▭▭▭▭ 1929        ← 훑기 막대 (창틀 = 지금 보이는 구간)

 1467 ─● 이시애의 난
 1498 ─● 무오사화
 1504 ─● 갑자사화             ← 고른 노드
 1506 ─● 중종반정
 1510 ─● 삼포왜란
```

**절대 연도는 위치를 말해주지 못한다.** '1504년'을 듣고 조선의 어디쯤인지
아는 사람은 드물다. 사람이 실제로 쓰는 좌표는 아는 사건과의 앞뒤다 —
"무오사화 다음, 중종반정 직전". 그래서 고른 노드 하나만 찍지 않고 세 겹을
함께 세운다: 노드 자신 · 연도를 아는 **직접 이웃** · 그 무렵의 **큰 사건**.

**축은 언제나 그래프가 담은 처음 해부터 끝 해까지다.** 고른 노드 언저리만
잘라 보여주면 위아래로 훑어도 시대의 양 끝에 닿지 못한다. 조선 그래프는
1356~1929년이고, 어느 노드를 골라도 같은 축 위에 선다 — 그래서 노드를
옮겨 다니며 자리를 견줄 수 있다.

**줌은 자리가 아니라 밀도를 바꾼다.** 지도가 멀리서는 큰 도시만, 가까이
가면 동네까지 보여주듯이, 연표도 멀리서는 큰 사건만 세우고 가까이 갈수록
더 많은 사건을 세운다 (`−`/`+` 단추, ⌘+휠, 트랙패드 핀치).

```
1/5   시대 전체가 한 화면     큰 사건 13 / 156     ← 처음 열면 이 단계
2/5   눈금 ×2               22
3/5   눈금 ×4               36
4/5   눈금 ×8               48
전부  눈금 ×16              156                   ← 다 세운다
```

무엇이 '큰' 사건인지는 그래프가 정한다. 많이 연결된 사건부터 자리를 잡고,
이미 선 것과 겹치는 자리(30px 안)에 오는 사건은 그 단계에서 물러난다.
눈금이 두 배가 되면 겹치던 자리가 벌어져 다음 사건이 들어온다. 비어 있는
구간에서는 작은 사건도 0단계부터 선다 — 빈 땅에 작은 마을을 그리는 것과
같다. 고른 노드·그 이웃·왕조는 단계와 무관하게 늘 선다: 배경이 아니라
그 노드의 이야기다.

**빠진 사건이 없는 셈이 되면 안 된다.** 그래서 머리에 `큰 사건 13 / 156 ·
더 보려면 +` 를 늘 적는다. 마지막 단계는 밀도 상한을 풀고 연대를 아는
사건을 다 세운다 — 1590년대에 20건이 몰려 라벨이 서로를 밀어내지만, 밀린
만큼은 가는 안내선으로 제자리와 이어 두는 것으로 갚는다. 조선 그래프의 뼈대는
157개다.

줌은 들여다보던 해를 지킨다 — 휠은 커서 아래, 단추는 고른 노드. 다른
노드를 골라도 배율은 그대로고(가까이 보던 사람이 멀어지면 안 된다),
새로고침해도 남는다.

**왕조 자신도 세운다.** 조선은 `org` 라서 사건 뼈대에 못 들어오는데, 빼
두면 연표에 건국이 없는 시대가 된다 — 훑으면 위화도 회군(1388) 다음이
곧장 제1차 왕자의 난(1398)이었다. 왕조 노드가 자기 존속 기간
(1392-08-13 ~ 1897-10-12)으로 서고, 500년을 가로지르는 막대는 축 **옆에**
비켜 세운다. 축 위에 겹쳐 그리면 그 위의 사건 점을 다 덮는다.

그래프에 `조선 건국` 이라는 사건 노드가 있기는 하다. 날짜가 없고 엣지가
둘뿐인 추출 고아라, 거기에 왕조의 P571 을 옮겨 적는 것은 **추측**이 된다.
아는 것을 아는 자리에 두는 편이 맞다.

**이름도 해도 같으면 한 줄만 세운다.** 실측: 임진왜란이 `wd:Q122846639`
(차수 37)와 `wd:Q576338`(차수 1) 둘로 있어 1592년 자리에 같은 이름이
나란히 찍혔다. 화면에서 둘은 구별되지 않으므로 많이 연결된 쪽만 남긴다.
**노드를 합치지는 않는다** — 라벨 유사도로 합치면 제1차/제2차 요동 정벌이
한 노드가 된다. 화면에서 보이는 것만 정리한다.

**한 번 언급된 추출 고아는 뼈대가 못 된다.** `ex:` 노드는 산문에서 이름만
뽑혀 나온 것이라, 엣지가 하나뿐이면 아무도 확인해 주지 않았다는 뜻이다.
실측: '1908년 복권'·'1963년 문집 간행'이 그렇게 들어와 축을 1963년까지
늘려 놓았다 — 사건 이름조차 아니다. 여럿이 가리키는 것은 남긴다.
진산사건(1791, 차수 3)이 1728~1791년의 빈 구간을 메운다.

**사람은 점으로 찍지 않는다.** 사건·작품만 연표의 점이 된다. 인물·장소·
조직은 이어지는 것이라 한 점에 찍으면 거짓을 말한다 — 윤필상(1427년생)을
갑자사화(1504) 옆에 '참여'라고 달아 1427년에 세우면 화면은 "1427년에
참여했다"고 읽힌다. 사람이 언제 살았는지는 **그 사람을 골랐을 때** 자기
자리에서 생몰 구간(막대)으로 말한다.

**날짜가 없어도 연도 노드를 타고 찾는다.** 조선 그래프의 사건 297개 중
`start_date` 를 가진 것은 73개뿐인데, 갑자사화처럼 `from_period` 로
`time:1504` 에 붙어 있는 것들이 있다. 다만 그렇게 알아낸 연도는 화면에
`연결된 연도` 라고 적어 둔다 — 노드가 스스로 적고 있는 날짜와 같은 얼굴로
내놓을 수는 없다.

**모르면 모른다고 말한다.** 연도도 없고 연도를 아는 이웃도 없으면 자리를
지어내지 않고 시대의 큰 사건만 펼친 뒤 "연도를 알 수 없습니다"라고 적는다.

시간 데이터가 지저분해서 세 가지를 걸러낸다.

| 걸러내는 것 | 실측 |
|---|---|
| 인물의 생년=몰년 | 서장옥이 1900-01-01 ~ 1900-01-01 (몰년만 아는 인물) |
| 지나치게 긴 구간 | 정축하성 1637~1895(258년) · 몰년 미상 인물의 `end_date` 가 2000 |
| 150년 밖의 이웃 | 갑자사화(1504) 참여자에 1955년생 정성근 — 그대로 두면 축이 450년으로 늘어나 정작 사화 앞뒤가 몇 픽셀로 뭉개진다 |

**자리는 연도에 비례한다.** 목록으로 늘어놓으면 1400년과 1401년 사이가
1400년과 1500년 사이만큼 벌어져 연표라고 부를 수 없다. 다만 라벨이 겹치면
못 읽으므로 밀어서 떨어뜨리고, **제자리와 밀린 자리를 가는 실선으로
잇는다** — 어긋난 만큼이 눈에 보여야 위치를 잘못 읽지 않는다.

그 안내선에 **노드 색을 쓰지 않는다.** 처음에는 노드 색 실선으로 그었는데
1398년에 '왕자의 난'과 '제1차 왕자의 난'이 나란히 서서 한 줄이 밀리자
**둘이 이어진 것으로 읽혔다** — 그때 그래프에는 둘 사이에 엣지가 하나도
없었다(그 결손은 `links` 가 메웠다). 안내선은 글자를 제자리에 데려다 놓는
표시이지 관계가 아니므로, **색을 빼고**(회색) 밀렸을 때만 긋는다 —
갈리는 것은 선의 모양이 아니라 색이었다.

**머리의 막대는 스크롤 손잡이다.** 좌우 끝은 이 연표가 담은 처음과 끝 해,
창틀은 지금 화면에 보이는 구간, 파란 표식은 고른 노드의 자리(인물이면 생몰
구간)다. 누르거나 끌면 그 해로 옮겨간다. **연표가 화면보다 길 때만 나온다** —
다 보이는데 '지금 보이는 구간'을 그리면 아무 말도 하지 않는 띠가 남는다.

**같은 단계면 같은 눈금이다.** 0단계는 시대 전체가 패널 한 화면에 들어오는
눈금이고 단계마다 두 배다. 축은 언제나 그래프 전체 범위라 어느 노드를
골라도 같은 눈금 위에 서고, 그래서 노드끼리 자리를 견줄 수 있다. 넘치는
만큼은 **스크롤**이 받는다. 노드를 고르면 그 자리로 스크롤이 맞춰지고,
훑다가 잃으면 머리의 연도를 눌러 돌아온다.

축 아래에는 64px 을 비워 둔다. 마지막 사건이 축 끝에 딱 붙으면 끝까지
내려도 패널 바닥과 '더 있다'는 그림자(28px)에 눌려 반쯤 지워진다.

연표는 폭을 250px 먹는다. 관계망만 크게 보고 싶으면 ☰ 패널의
`왼쪽 연표 보이기` 로 접는다.

### 조작 — 클릭하면 그 사람의 세계가 열린다

노드를 클릭하면 상세가 열리고 **그 주변이 함께 펼쳐진다**. 고르기만 하면
안 된다는 걸 실측으로 배웠다. 조선 화면에서 정종을 누르면 화면에는 그가
우연히 들고 온 선 하나만 남았다 — 실제로는 관계가 24건 있고 아버지
태조도, 형제인 태종·회안대군·익안대군도, 자녀 15명도 다 있는데.

```
조선 화면 안의 정종   관계 1개   ← 조선에 붙은 엣지만 그려진다
정종을 클릭         노드 76 · 관계 147   부모·형제·자녀·배우자·관직
```

펼침은 기존 배치에 **얹는다**. 화면이 통째로 튀면 방금 보던 것을 잃는다.
드래그는 고정, 휠은 확대. 주소창에 지금 보는 노드가 남아서 새로고침해도
자리를 잃지 않고 링크로 넘길 수 있다. 헤더의 시대 칩을 누르면 언제든
중심(왕조)으로 돌아온다.

### 설계 원칙

- **실패는 시끄럽게.** 쿼리 실패 시 빈 리스트를 반환하면 "데이터 없음"과
  구분되지 않아 결손된 그래프를 완전한 것으로 착각한다. 예외를 던지고,
  부분 실패는 수집 끝에 반드시 목록으로 보고한다.
- **실패 응답은 캐시하지 않는다.** 활용신청 승인 후에도 옛 에러가 계속
  돌아오는 것을 막는다.
- **인증키는 로그·예외 메시지에서 마스킹한다** (`http.redact`).
- **모든 엣지는 출처를 갖는다.** `(src, dst, type, source)` 가 자연키라
  같은 사실을 여러 소스가 말하면 각각 남아 교차검증에 쓸 수 있다.
- **스키마 불일치는 버리지 않고 완화한다.** 실제 P31 타입이 엣지 스키마와
  안 맞으면 `related_to` 로 낮추고 원래 타입을 `props` 에 남긴다.
- **자기순환은 만들지 않는다.** 아무 사실도 말하지 않고 화면에도 그릴 수
  없다. 두 군데서 새고 있었다 — `timeline` 이 연도 노드를 자기 자신에
  잇고(1,253건), 추출이 '기사환국은 기사환국과 관련된다'를 냈다.

## 온톨로지

**노드** — 인물, 사건, 장소, 예술작품, 유물·문화재, 영화·드라마,
단체·국가·왕조, 시대, 직위·칭호, 개념·주제

**엣지** — 참여, 발생 장소, 발생 시기, 출생지, 사망지, 제작, 소재지,
소재로 다룸, 주제, 배경, 자녀, 배우자, 소속, 직위, 시대, 상위, 관련

**개념·주제**는 사상·제도·풍습·소재가 앉는 자리다. 이 자리가 없으면 개념이
사건 행세를 한다 — "개념이 사건 행세를 하고 있었다" 참조. 작품이 **실체**를
다루면 `depicts`(소재로 다룸), **주제어**를 다루면 `about`(주제)이다.
`set_in`(배경)은 작품이 다루는 시대·장소로, 개봉연도와 다른 축이다.

작품(`media`)은 **매체 구분**(`props.form` — 영화·드라마·다큐멘터리·
애니메이션·책·만화·게임·음악·무대)을 반드시 갖는다. 노드 타입을 매체별로
쪼개지 않는 이유와 그 관문은 "작품 명단은 분류에 있다" 참조.

노드 ID 는 `{source}:{native_id}` (`wd:Q37682`, `khs:11-11-0000010000000`).
소스 간 동일 개체 연결은 `same_as` 테이블이 담당한다.
