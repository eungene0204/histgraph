# histgraph — 한국사 온톨로지 그래프

역사를 인물·사건·장소·작품·유물·영상물의 노드와 엣지로 연결해 보여주는
프로젝트. 이 저장소는 그 **데이터 수집 파이프라인**이다.

## 빠른 시작

```bash
cp .env.example .env        # 인증키 입력
export PYTHONPATH=src

python3 -m histgraph doctor                          # 소스별 접근 진단
python3 -m histgraph ingest heritage --kinds 11 12   # 국보·보물 수집
python3 -m histgraph ingest wikidata                 # 인물/사건/영상물 수집
python3 -m histgraph prune                           # 스포츠 이벤트 제거 (필수)
python3 -m histgraph resolve                         # 소스 간 엔티티 연결
python3 -m histgraph events                          # 한국사 주요 사건 직접 수집
python3 -m histgraph enrich --limit 1200             # 위키백과 서사로 노드 보강
python3 -m histgraph extract --dry-run               # 추출 프롬프트 확인
python3 -m histgraph extract --min-score 2.0 --limit 50   # 관계 추출 (배치)
python3 -m histgraph stats                           # 그래프 통계
python3 -m histgraph show wd:Q37682 --depth 2        # 세종 주변 서브그래프
```

**`prune` 은 선택이 아니라 필수입니다.** 아래 "스포츠 오염" 참조.

의존성 없음 (Python 3.11+ 표준 라이브러리만 사용).

## 설계에서 가장 중요한 사실

**공공 API 는 개체를 주지만 관계를 주지 않는다.** 그래프의 가치는 엣지에
있는데, 국가유산청·공공데이터포털은 유물 속성(명칭·소재지·시대)은 잘 주지만
"누가 이 사건에 참여했는가" 같은 관계는 제공하지 않는다.

Wikidata 조차 부족하다. 실측치:

| 관계 (조선) | 엣지 수 |
|---|---|
| 직업 P106 | 3,595 |
| 자녀 P40 | 647 |
| 출생지 P19 | 431 |
| 아버지 P22 | 402 |
| **참여 사건 P1344** | **35** |

계보·출생지는 수집으로 채워지지만, **역사 서사의 핵심인 인물↔사건 엣지는
거의 존재하지 않는다.** 이 엣지는 산문(국가유산청 `content`, 실록 원문,
백과사전 항목)에서 추출해야 한다. `Edge.confidence` 필드가 그 대비다 —
구조화 소스는 1.0, 텍스트 추론은 그 미만으로 기록해 신뢰도를 구분한다.

### 스포츠 오염 — 총계만 보면 속는다

정체 9개로 넓혀 수집하면 `participated_in` 이 5,791건까지 늘어난다.
충분해 보이지만 **90.5%가 올림픽·아시안게임 출전 기록**이었다.

| 단계 | participated_in |
|---|---|
| 수집 직후 | 5,791 |
| 라벨 정규식 제거 후 | 125 |
| Wikidata 클래스(P279*) 제거 후 | **85** |

남은 85건이 진짜다 — 국채보상운동(26), 제1차 왕자의 난(6), 계유정난,
전조선 제정당사회단체 대표자 연석회의. 처음 조선만 측정했을 때의 35건과
같은 크기다. 정체를 넓혀도 역사 엣지는 늘지 않았다.

**교훈: 엣지 총계가 아니라 대상 노드의 라벨 분포를 봐야 한다.**
필터는 라벨 정규식만으로는 부족하다 — 'Konica Cup', 'Superseries',
'Internationaux de France' 는 이름만으로 스포츠인지 알 수 없다.
Wikidata 의 P279* 계층에 직접 물어보는 2차 필터가 필요하다.

### 두 개의 섬 — 엔티티 해소

국가유산청 그래프와 Wikidata 그래프는 기본적으로 서로 닿지 않는다.
숭례문에서 세종으로 가는 경로가 없으면 온톨로지 그래프로서 작동하지 않는다.

접합점은 **장소와 시대**다. 국가유산청은 유물마다 시도·시군구(`ccbaCtcdNm`,
`ccsiName`)와 시대(`ccceName`)를 주고, Wikidata 는 같은 지명과 왕조를
항목으로 갖고 있다. `resolve` 가 이 둘을 `same_as` 로 잇는다.

- 시대: 매핑표 기반 (조선시대 → `wd:Q28179`), score 1.0
- 장소: 정규화 후 정확 일치 (`서울특별시` → `서울`), score 0.9.
  후보가 둘 이상이면 잇지 않는다 — 자동으로 고르면 틀린 곳에 붙는다.

`resolve` 는 끝에 **연결 검증**을 출력한다. `same_as` 행 수만 세면
"연결된 것 같다"는 착각을 하기 쉬우므로, 소스를 건너뛰는 링크 수와
국가유산청 노드에서 Wikidata 로 실제로 나가는 경로 수를 함께 센다.

## 소스 현황

| 소스 | 상태 | 인증 | 제공 |
|---|---|---|---|
| 국가유산청 Open API | ✅ 동작 | 불필요 | 유물·문화재, 시대, 소재지, 4단계 분류 |
| Wikidata SPARQL | ✅ 동작 | 불필요 | 인물, 사건, 영상물, 관계 엣지 |
| 공공데이터포털 data.go.kr | ⛔ 대기 | 키 있음 + **데이터셋별 활용신청** | 유물정보, 문화재 공간정보 |
| 문화공공데이터광장 culture.go.kr | ⛔ 대기 | 키 있음 + **API별 활용신청** | 박물관 소장품 |

### 활용신청이 필요하다

두 포털 모두 **키가 유효해도 데이터셋마다 따로 신청**해야 한다.

- data.go.kr → `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` (코드 30)
- culture.go.kr → `{"message":"Unauthorized","http_status_code":401}`

`doctor` 가 이 상태를 데이터셋별로 진단한다. 승인 후 `datagokr.py` /
`culture.py` 의 `CANDIDATES` 에 실제 엔드포인트 경로를 채우면 된다
(현재 등록된 경로는 미검증 추정값이라 `[12] 존재하지 않는 서비스`가 난다).

## 실측으로 알아낸 API 함정

- **국가유산청 상세 조회**는 목록이 주는 **13자리** `ccbaAsno` 를 그대로
  써야 한다. 8·10자리로 자르면 에러가 아니라 **HTTP 200 에 빈 필드**가
  돌아와 조용히 실패한다.
- **왕조 QID 를 추측하면 반드시 틀린다.** Q34049 는 고려가 아니라 셈어파,
  Q28194 는 고구려가 아니라 독일 가수다. `doctor` 가 기대 라벨과 대조해
  검증한다.
- **WDQS 는 60초 제한**이 있다. 정체 9개를 `VALUES` 로 묶고 label service 를
  붙이면 타임아웃난다. 정체별로 쪼개고 라벨은 별도 배치로 조회한다.
- **WDQS 는 과호출에 403/429/502** 로 응답한다. 요청 간격 1.5초 이상 권장.
- **공공 API 는 인증 실패도 HTTP 200 으로 준다.** 본문의 `errMsg` 를 봐야
  한다.

## 산문의 종류가 결과를 좌우한다

"산문에서 추출하면 된다"는 말은 절반만 맞다. **어떤 산문인지가 중요하다.**

국가유산청 `content` 2,903건을 표지어로 훑어본 결과:

| 구분 | 문서 수 | 비율 |
|---|---|---|
| 인물 표지 있음 | 1,538 | 53% |
| 사건 표지 있음 | 1,099 | 38% |
| **둘 다 있음** | **634** | **22%** |
| 서지·규격 기술 | 788 | 27% |

가장 긴 문서(5,023자)를 열어보면 이렇다:

> 상하단변(上下單邊), 좌우쌍변(左右雙邊)에 반곽(半郭) 24.5×15.8cm, 무계(無界)이며,
> 반엽의 행자수는 17행 34자, 판심에는 '진 제오십일(晋第五十一)'…

**유물 해설문은 "이 물건이 무엇인가"를 적은 글이다.** 우리가 필요한 건
"누가 무엇을 했는가"다. 길이순으로 문서를 고르면 가장 긴 문서가 판본
치수 나열이라 API 비용이 그대로 헛돈다.

그래서 두 가지를 했다.

**1. 서사 점수로 문서를 선별한다** (`extract --min-score`). 인물·사건
표지에 가점, 서지·규격 표지에 감점. 길이는 약한 보정으로만 쓴다.

```
전체 2,903건 → min-score 1.0: 1,745건 → min-score 2.0: 619건
```

**2. 진짜 서사 코퍼스를 붙였다** (`enrich`). 실록과 백과사전은 활용신청
대기 중이라, 지금 막힘 없이 쓸 수 있는 건 한국어 위키백과뿐이다.

비교해보면 차이가 분명하다:

| 출처 | 예시 |
|---|---|
| 국가유산청 | `반곽 24.5×15.8cm, 무계이며 행자수는 17행 34자` |
| 위키백과 | `박정희는 … 1979년 10·26 사건 당시 김재규 전 중앙정보부장의 총격으로 서거하였다` |

## 위키백과 보강 (`enrich`)

새 노드를 만들지 않는다. Wikidata 항목에 달린 한국어 위키백과
**sitelink** 를 따라가 기존 노드의 `description` 을 채운다. 새로 만들면
엔티티 해소를 또 해야 하지만, sitelink 는 QID 가 곧 키라서 정확히 같은
노드에 꽂힌다.

- 노드 라벨을 문서명으로 쓰면 안 된다 — 우리 라벨은 `조선 세종`인데
  실제 문서명은 `세종`이라 조회가 빗나간다.
- 연결 차수 상위순으로 고른다. 3만 건을 다 받는 건 비현실적이고,
  많이 연결된 인물이 문헌에도 자주 등장한다.
- 인증키 불필요. 단 **User-Agent 는 필수** — 없으면 Wikimedia 가
  JSON 대신 오류 HTML 을 돌려준다.
- 도입부는 한 요청에 20건(인물 항목 기준 900~1,400자), `--full` 은
  본문 전체지만 요청당 1건이다.

## 핵심 사건 직접 수집 (`events`)

차수 상위순으로 고르는 `enrich` 로는 **임진왜란·병자호란이 잡히지 않는다**
— Wikidata 상에서 연결이 적기 때문이다. 이름으로 직접 지정하는 경로가
따로 필요하다.

분류 순회를 먼저 시도했으나 쓸 수 없었다. 한국어 위키백과의 사건 분류는
일관성이 없고(`분류:한국의_전쟁`, `분류:조선의_사건` 은 아예 없음), 실제
문서에 달린 분류는 `1636년 분쟁`, `깨진 링크를 가지고 있는 문서` 같은
연도·정비 분류가 대부분이다. 도메인 지식으로 직접 나열하는 편이 정확했다.

시드는 시대별로 묶여 있어 사건마다 `from_period` 엣지를 공짜로 얻는다.
문서명은 `extracts`+`pageprops` 한 요청으로 QID까지 함께 받아 `wd:Qxxxx`
노드로 만든다 — 기존 Wikidata 사건 노드와 자동으로 합쳐진다.

**본문 전체를 받는 것이 핵심이다.** 도입부만 받으면 사건 평균 380자인데,
"누가 무엇을 했는가"는 대부분 본문에 있다:

```
도입부만: 평균   380자 → 추출 대상 사건 33건
본문 전체: 평균 7,733자 → 추출 대상 사건 91건   (6·25 전쟁은 57,451자)
```

### 긴 문서는 조각낸다

본문 전체를 통째로 한 요청에 넣으면 뒤쪽 문단의 관계를 놓친다. 6,000자
단위로 **문단 경계에서** 자르고 400자씩 겹친다. 문단 중간에서 자르면
`이순신은 …` / `… 명량에서 승리했다` 처럼 주어와 서술이 갈라져 관계가
통째로 사라진다.

## 산문에서 관계 추출 (`extract`)

인물↔사건 엣지의 유일한 현실적 공급원. Claude API(`claude-opus-5`)로
산문에서 관계를 뽑는다.

- **가제티어 그라운딩** — 그래프에 이미 있는 개체명을 프롬프트에 넣어
  모델이 같은 표기를 쓰게 한다. 이게 없으면 추출 결과가 기존 노드에
  붙지 않는 고아가 되어 그래프가 연결되지 않는다.
- **structured outputs** — `output_config.format` 의 JSON 스키마로 응답
  형태를 강제한다. 파싱 재시도 루프가 필요 없다.
- **Batch API 기본값** — 추출은 실시간성이 필요 없으므로 표준 요금의
  50%인 배치로 처리한다. `--sync` 는 소량 테스트용.
- **근거 보존** — 모든 추출 엣지는 원문 구절을 `props.evidence` 에 남긴다.
  출처 없는 추론은 나중에 검증할 수 없다.
- **거절 처리** — Claude Opus 5 는 안전 분류기가 요청을 거절할 수 있다
  (HTTP 200 + `stop_reason: "refusal"`). `content` 를 무조건 인덱싱하면
  거기서 깨지므로 먼저 `stop_reason` 을 확인한다.

비용을 쓰기 전에 `extract --dry-run` 으로 실제 프롬프트를 확인할 것.

## 구조

```
src/histgraph/
├── ontology.py   노드 9종 · 엣지 15종 스키마 + 양끝 타입 검증
├── http.py       디스크 캐시 · 레이트리밋 · 백오프 재시도 · 키 마스킹
├── store.py      SQLite 그래프 저장소 (멱등 upsert, 서브그래프 조회)
├── filters.py    스포츠 오염 필터 (판정은 is_sports() 하나로 단일화)
├── resolve.py    엔티티 해소 · 스포츠 제거 · 연결 검증
├── extract.py    Claude API 관계 추출 (구조화 출력 + 배치)
├── cli.py        doctor / ingest / prune / resolve / extract / stats / show
└── sources/
    ├── heritage.py   국가유산청
    ├── wikidata.py   Wikidata SPARQL
    ├── wikipedia.py  한국어 위키백과 (서사 코퍼스)
    ├── datagokr.py   공공데이터포털
    └── culture.py    문화공공데이터광장
```

### 설계 원칙

- **실패는 시끄럽게.** 쿼리 실패 시 빈 리스트를 반환하면 "데이터 없음"과
  구분되지 않아 결손된 그래프를 완전한 것으로 착각한다. 예외를 던지고,
  부분 실패는 수집 끝에 반드시 목록으로 보고한다.
- **실패 응답은 캐시하지 않는다.** 활용신청 승인 후에도 옛 에러가 계속
  돌아오는 것을 막는다.
- **인증키는 로그·예외 메시지에서 마스킹한다** (`http.redact`).
- **모든 엣지는 출처를 갖는다.** `(src, dst, type, source)` 가 자연키라
  같은 사실을 여러 소스가 말하면 각각 남아 교차검증에 쓸 수 있다.
- **스키마 불일치는 버리지 않고 완화한다.** 실제 P31 타입이 엣지 스키마와
  안 맞으면 `related_to` 로 낮추고 원래 타입을 `props` 에 남긴다.
